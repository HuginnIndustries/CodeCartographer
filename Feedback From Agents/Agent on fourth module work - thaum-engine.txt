(`thaum-protocol`, `thaum-providers-ollama`, `thaum-sandbox`), and a

Date: 2026-05-02
Model: Claude (anthropic)
Session: module-4 (`thaum-engine` v0) — fourth code-producing session
against this codecarto bundle. The engine is the central module —
where the SQ/EQ contract, the Outcome newtype, and the two-tier
intervention queue stop being spec text and become load-bearing
primitives.


WHAT WORKED REALLY WELL
=======================

1. Typed-seam discipline as a v0 anti-creep mechanism.

   The prompt explicitly listed five leaf modules that don't exist yet
   (state, tools, hooks, exec-policy, sandbox) and said: "v0 stubs each
   at clean seams; future sessions slot real implementations in." That
   single instruction shaped the whole architecture. I wrote
   `StateSeam.noOp()`, `ToolsSeam.noOp()`, `HooksSeam.noOp()`,
   `ExecPolicySeam.allowAll()`, `SandboxSeam.noOp()` — each a typed
   interface with a v0 default and a doc-comment naming the future
   module that will replace it.

   Critically: `ExecPolicySeam.allowAll()` is named to be a tripwire.
   Anyone reading `engine.ts` and seeing `ExecPolicySeam.allowAll()`
   immediately knows they're looking at a v0 development stub, NOT a
   production policy. The spec's Δ-DD1.4 is explicit that exec policy
   MUST fail-closed at startup; the v0 stub deliberately violates that
   in a way that NAMES the violation. This is the right design for a
   port: the next session implementing `thaum-exec-policy` cannot ship
   without searching for `allowAll()` and replacing it.

   Three modules ago this would have been fragile. The pattern is now
   the codecarto convention: name v0 stubs to scream "I am a stub."

2. The Outcome newtype actually paid off.

   The spec's Spike List #11 demanded "the dispatcher cannot construct
   an Outcome without calling sink.respond/error/defer." When I wrote
   the dispatcher, every Op variant arm had to return `sink.respond(...)`,
   `sink.error(...)`, or `sink.defer(...)` — there was no third option
   that compiled. I caught at least two arms where I almost wrote a
   "side-effect-only, no response" variant; the type system blocked it.

   Net effect: the dispatcher's "Submission MUST NOT hang" invariant is
   compile-time-enforced, not runtime-enforced. The spec made the cost
   of getting this wrong visible — codex itself shipped with
   `console.warn`-only arms — and the type system delivers on the
   contract.

   The `defer` variant was load-bearing: `Op.userTurn` and `Op.shutdown`
   genuinely need it (the response arrives later via the EQ, not
   synchronously from the dispatcher). Without `defer`, the dispatcher
   would have to fake a response or block. The fact that the protocol
   layer baked `defer` in from day one is what made the engine's
   dispatcher pure.

3. Verbatim spec quotes at load-bearing seams.

   The Δ-22 discipline ("paste the spec's exact wording in a comment
   block above the code that implements it") carried over naturally to
   the engine. I cited four spec rules verbatim in code:
     - dispatcher.ts above the Op.userTurn arm — preemption invariant
     - queue.ts above the snapshot emission — full-snapshot semantics
     - turn.ts above the partialJson accumulator — Δ-7 opacity
     - task.ts above the FSM intro — canonical home for preemption
   A future maintainer reordering or weakening any of these has to walk
   PAST the spec citation. This is not just documentation — it's a
   dead-man's switch for the invariant.

4. The session prompt's "Discipline" section.

   This was the single highest-signal block in the prompt. Specific items
   that shaped the implementation:

   - "Resist scope creep" with named anti-patterns ("the spec calls out
     codex-core as a kitchen-sink anti-pattern; AGENTS.md explicitly
     warns against it"). Without this I would have considered putting
     persistence into the engine.

   - "Use the Outcome newtype religiously in the dispatcher. Every
     dispatcher arm calls OutcomeSink.respond/error/defer. There is no
     `// no response` arm." Naming the mistake to avoid was effective.

   - "No I/O without an injected slot." This was the rule that made me
     refactor my first draft (which used raw `crypto.randomUUID`) into
     `EngineTestHooks { provider, sandbox, clock, idGenerator }`. Now
     every test runs with a deterministic clock and id generator —
     deterministic tests are not a guideline, they're a build product.

   - "Generalize the test-injection pattern. This session is the third
     instance — Ollama needed fetch, sandbox needed spawnHelper, engine
     needs provider/sandbox/clock/idGenerator. Lift if it generalizes;
     document why if it doesn't." This is the BEST kind of guidance
     because it forces an actual decision rather than mechanical
     compliance. I decided NOT to lift `EngineTestHooks` to
     `thaum-protocol` because the slot SETS diverge per module — and
     documented the reasoning in `src/test-hooks.ts` so the FOURTH
     instance doesn't relitigate.

5. The closeout ritual remains the right shape.

   THREAD_LOG entry → status.yaml `next_actions` update → "decisions
   beyond prompt" record. By the time I wrote my session entry I knew
   exactly what would help the `thaum-state` session: which seam to
   implement, what its current `noOp` shape returns, where the spec
   sections are, what's blocked on what.

6. The "next session" hand-off in status.yaml.

   I started the session by reading `next_actions` and saw "thaum-engine
   (the SQ/EQ orchestrator that wires thaum-providers-ollama, thaum-
   sandbox, and the future nested-tool host together)." That single
   bullet contained the architectural position, the dependencies, and
   the scope. I ended the session by appending a "thaum-engine v0 DONE"
   bullet and updating the next-step bullet to point at `thaum-state`.
   The handoff baton works.


SOME FRICTION
=============

1. The spec file's read-cost.

   `reimplementation-spec.md` was 42 KB and 237 lines (some lines >500
   chars). I couldn't `Read` the whole thing without hitting context
   limits, so I used `grep` to find section boundaries and then
   `Read offset/limit` to read 90-100-line slices. This worked, but the
   workflow was: scan H2/H3 headings → grep for keywords from the prompt
   (e.g. "Δ-7", "Outcome", "preempts") → read the surrounding paragraph.
   Each round-trip cost a tool call and a slice of context.

   Suggestion: the spec could ship in chunks. A `spec/` directory with
   `00-system-summary.md`, `01-modules.md`, `02-required-behaviors.md`,
   etc. plus a `spec/INDEX.md` would let an implementer pull only the
   sections relevant to the current module. The spec file as it stands
   is optimized for a human reading top-to-bottom; a per-section file
   layout would be optimized for an implementer reading "what's the
   contract for this Op."

2. status.yaml `next_actions` scaling, again.

   By the end of my session there were 11 entries in `next_actions`.
   This includes module-completion records ("thaum-engine v0 DONE"),
   the next-step pointer ("module-work kickoff sequence"), pending
   spec-deltas (Δ-36, Δ-37), the round-3 spike, and the conformance
   tests required before shipping. It's still readable but the second
   feedback file flagged this and the third (mine) is hitting it again.

   The schema-split suggestion from the prior feedback is still right:
     completed_modules: [{ name, date, commit, tests }]
     next_module: { name, prerequisites, blocked_on }
     pending_deltas: [{ id, source_session, target_session }]
     conformance_gates: [{ name, target_session }]
   At 11 unstructured bullets the array is doing four jobs.

3. Filesystem sync flake during the closeout.

   I tried to append my session entry to THREAD_LOG.md three times via
   bash heredoc; each time the bash mount reported success but the host
   view either stayed the same OR truncated some prior entry. Eventually
   the `Edit` tool (via the host path) was the only way to make the
   write durable. Spent ~10 minutes diagnosing.

   This is not a codecarto issue per se — but the framework's heavy
   reliance on append-to-narrative-files (THREAD_LOG.md, status.yaml,
   the spec) magnifies the cost of a sync flake. A defensive convention
   would be: every closeout writes a SEPARATE file (`closeouts/2026-05-
   02-thaum-engine.md`) and the THREAD_LOG.md is the concatenation, not
   the source of truth. Same for `next_actions` — each session writes a
   per-session decision log, and `status.yaml`'s `next_actions` is a
   recomputed view.

4. THREAD_LOG.md is approaching the size where Read-without-offset is
   risky.

   The file was 90+ KB by the time I wrote my entry. A `Read` against
   it without offset failed silently in places (showed the head, not
   the tail). I worked around with `grep -n "^## "` to find section
   boundaries and `Read offset` for each section. Same per-session-file
   suggestion as above would solve this: a `THREAD_LOG/2026-05-02-thaum-
   engine.md` per session, plus an `INDEX.md` listing them, scales
   forever without a single-file read budget.

5. Spec/code drift on `'allowedLoopback'` vs `'allowed-loopback'`.

   The thaum-protocol enum is canonical at `'allowedLoopback'` (camelCase
   as documented in the spec's Round-2 deltas), but parts of the spec
   text still use the hyphenated `'allowed-loopback'` form. This was
   flagged by the previous session as "Δ-37 (proposed, not yet applied)";
   I observed the same drift while writing the engine's seam types.
   Pending a spec-revision pass, the convention is "trust the typed
   surface in thaum-protocol." This works, but it's a risk: an
   implementer who reads only the spec text and doesn't import from
   thaum-protocol might rebuild the enum with the kebab form.

   Suggestion: the next spec-revision pass should grep for `'allowed-
   loopback'` in the spec text and reconcile to `'allowedLoopback'` in
   one go. Same for any other canonical-form-elsewhere drift items.

6. Test-injection pattern is documented in three places.

   The convention ("Config interface + all-optional injection slots +
   ResolvedConfig with defaults applied") is documented in:
     - `thaum-providers-ollama/src/config.ts` (origin)
     - `thaum-sandbox/src/client.ts` (second instance)
     - `thaum-engine/src/test-hooks.ts` (third instance, with the
       lift-decision rationale)
     - the README of each
   That's a lot of duplication. A `.codecarto/CONVENTIONS.md` page that
   names the pattern once ("Test-Injection Slots: Config interface
   pattern, applied per-module, lift-decision criteria are X/Y/Z") and
   that all three modules link to would be more durable. The same
   probably applies to the verbatim-spec-quote-in-code convention and
   the v0-stub-naming convention (`allowAll()` etc.).


WHAT MIGHT HELP THE NEXT MODULE-WORK SESSION
============================================

1. Per-session closeout files (see friction #3, #4). Splitting the
   monolithic THREAD_LOG.md and `next_actions` array into per-session
   pieces keeps individual writes small and atomic.

2. A `.codecarto/CONVENTIONS.md` index. The conventions that compound
   across module-work sessions — typed seams with named v0 stubs,
   test-injection slots, verbatim-spec-quotes-in-code, `Outcome`
   newtype discipline — should live in ONE document that the session
   prompt links to. Today they're rediscovered (or partially missed) by
   each new implementer.

3. A `bun run spec:check` script (carried forward from the prior
   feedback). Same justification: prevents silent truncation, codifies
   the section-presence invariants. Add: a check that every Δ-N
   referenced in the body has a matching row in the deltas-table.

4. A pre-implementation seam-audit document. The engine's v0 has five
   seams; each seam has a doc-comment naming the future module that
   will replace it. The next session implementing `thaum-state` should
   be able to look up a single page that says: "engine's StateSeam
   shape is X; thaum-state must implement that shape; the engine's
   `noOp()` default returns Y." This is reconstructible from the engine
   source today, but a single SEAMS.md would mean the implementer
   doesn't have to read engine code to know what they're being asked
   to fulfill.

5. A `MODULES.md` (carried from the prior feedback). Tabular at-a-glance
   view of module status across the whole port. After 4 modules the
   need is more obvious than at 2.

6. A "decisions beyond prompt" rolled-up index. Each session's
   THREAD_LOG entry has a "decisions made beyond prompt" section. After
   four sessions there are ~25 such decisions across the codebase
   (channels split into two impls, Outcome as brand newtype,
   discriminator field as `type`+camelCase, `imageInput: false` for
   Ollama v0, etc.). Some are local to one module; some — like the
   discriminator-field decision — are cross-cutting. Rolling them up
   into `.codecarto/DECISIONS.md` would turn the historical record into
   a forward-facing reference for future modules.


OVERALL
=======

The codecarto framework's discipline of "spec → contracts → protocols →
porting → reimplementation-spec → module-work" continues to be the
right shape, four sessions in. The high-leverage conventions —
verbatim-spec-quotes-in-code, the Outcome newtype, the closeout ritual,
the typed-seams-with-named-v0-stubs pattern — compound. Each module-
work session can be smaller because the previous session's invariants
are encoded into the type system (Outcome), into source comments
(spec quotes), into tripwire names (`ExecPolicySeam.allowAll()`), and
into the status.yaml handoff baton.

The friction is consistent across sessions: (a) the spec and THREAD_LOG
are getting big enough that the file-size becomes a workflow tax, (b)
the `next_actions` array is doing too many jobs, (c) cross-cutting
conventions need a single home rather than being rediscovered per
module. None of these are blockers; they're scaling pains that suggest
codecarto could grow a small index/conventions/decisions layer between
the spec and the per-module sources.

The thing I'd most want next time: a "v0 contracts" subset of the spec
that names which invariants are load-bearing-NOW vs nice-to-have-LATER.
The engine v0 stops short of approval flow, exec policy, persistence,
hooks, tools — but the spec's §Required Behaviors lists all of those
as MUST. An "implementing v0?" view would say: "for v0 of this module,
honor invariants A/B/C; D/E/F land in modules X/Y/Z." Today the
implementer infers this from the session prompt + the typed seams; a
spec annotation would make it durable.
