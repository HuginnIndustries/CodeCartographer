#Feedback from an agent coordinating the results from other strings.

Yes, I have substantive feedback. The framework is good — the pipeline went six phases without procedural drag, and the deliverables are usable artifacts. But there are real gaps, and the parts that work best are not always the parts that get the most attention in the docs.
What works (and would be missed if removed)
The validation gate. Forcing PASS / PASS WITH GAPS / FAIL with a criterion-by-criterion citation table at the bottom of every primary output is the single most disciplining feature. Without it I'd have shipped softer outputs. Re-validation after the open-question pre-pass worked cleanly. Don't change this.
Append-mode secondary outputs. This is the framework's quiet superpower. Reading state-and-storage.md after the pipeline closes, you can watch the same SQLite story accumulate ("29 migrations" → "logs moved to dedicated DB" → "logs at logs_2.sqlite, separate pool, 10-day retention" → "archive-by-default migration policy"). The dated phase sections create a record of how understanding grew, not just what's known. Most frameworks throw away that history.
Pipeline variants. Five is the right number. The full-with-audit / full / lite / defect-scan-only / architecture-only split actually maps to real use cases. The user picking a variant up front, with the YAML enforcing the phase set, kept scope honest.
Trust boundaries (read-only vs writable). The table at the top of GUIDE.md is small but load-bearing. Made it impossible to accidentally modify a SKILL.md or pipeline YAML. Should be the first thing every framework defines.
Skill files with structured prompts. The architecture SKILL.md's "Test for common structural patterns" list (shared provider layer, agent loop, multiple delivery surfaces, plugin architecture, etc.) actually changed how I clustered. Without that nudge I might have written a flat package list. Templates removed the blank-page problem; SKILLs removed the wrong-shape problem.
What had friction (real, not nitpicks)
open_questions is one field doing two jobs. Real unknowns and "deferred to later phase" both end up there, distinguishable only by whether I added a [carry-forward → defect-scan] tag I had to invent. Should be two fields: open_questions (still genuinely unknown) and carry_forward (resolved by the framework's later phases, with explicit phase target). Schema mismatch caused real friction at every phase handoff.
Phases overlap in practice; the framework presumes clean handoffs. Defect-scan resolved architecture questions. Contracts pinned defect findings as port contracts. Protocols pinned contracts at wire level. The strict phase boundary worked, but the receiving phase had to know to look back for resolved items, and there's no machinery for that. A "previously resolved" footer in each output would help; better still, a resolutions/ directory the next phase reads automatically.
No "strategic alignment" hook before the synthesis phase. Our discussion before the reimpl-spec — provider-agnostic, target stack, naming — produced inputs the spec actually needed. Without it the spec would have been generic. The framework has no place for that conversation. The reimpl-spec template defaults to "any port to any stack," which is the wrong tool when the user has specific opinions. A pre-spec strategic-alignment template (or just an explicit prompt: "Have you locked target stack, scope cuts, and project identity?") would have caught this.
The relationship between primary and secondary outputs is undocumented. I invented the rule "summaries in primary, details in secondary" because nothing in GUIDE.md specifies it. The architecture-map's Public Surfaces, Runtime Lifecycle, Build and Packaging sections directly overlap with the secondary outputs of the same names. Without a rule, those duplicate or contradict. Should be: primary owns the map and the load-bearing claims; secondaries own the catalog-level detail. Spell it out.
Subagent delegation isn't blessed. I leaned heavily on subagents for the 91-crate dependency walk and the Pi-mono comparison. The framework is silent on this. For codebases over some threshold (~50 source files? ~100K LOC?), explicit guidance on what to delegate would prevent the obvious failure mode of "burn primary context on extraction work." A two-line note in GUIDE.md would do it.
The reimpl-spec template defaults to generic-port mode. The user wanting an opinionated, named, target-specific spec was the most informative case I encountered, and the template offered no help. A second template variant — "specific named port with locked target stack" — would have skipped the strategic-alignment improvisation we did. Pi-mono's spec was already in this mode (named project, named modules, named primitives), so the pattern is proven.
Defect-scan didn't naturally fit a phase boundary. Two-pass (broad → deep) was a clean pattern that emerged from the conversation, not the framework. The defect report ended up with both passes appended into one file, which works, but the framework presumes "one pass = one phase output." A defect-pass-N append discipline (like secondary outputs) would have been more honest about how defect work actually plays out.
What I'd actually change
If you do another revision, in priority order:

Split open_questions into open_questions + carry_forward with explicit phase targets. Cheapest change, highest leverage.
Add a "primary vs secondary outputs" section to GUIDE.md. Two paragraphs. Specifies the summary-vs-detail rule.
Add an optional pre-synthesis strategic-alignment phase (or at minimum, a checklist the GUIDE prompts before reimpl-spec): target stack, project identity, scope cuts, named primitives. The reimpl-spec template gets a variant for "specific named port."
Add subagent guidance for large codebases. One paragraph. "Delegate dependency mapping, file inventories, and cross-document comparisons to subagents and cite their scratch artifacts."
Bless the multi-pass append pattern for defect-scan. Same model as secondary outputs: pass-N gets a dated section, no overwrites.
Add a resolutions/ mechanic so later phases can see what earlier phases resolved. Either a directory or an explicit footer in each primary output.

What I would not change: the validation gate, the append-mode secondary outputs, the trust boundaries, the pipeline variants, the skill files, the evidence-level discipline. Those are the load-bearing parts and they earned their weight.
The framework's biggest strength, which the docs underplay: it makes honest output the default. The validation block can't be skipped, evidence levels can't be left blank, the open-questions field is in your face at every status update. Most agent frameworks let you ship slop. This one doesn't. Worth saying out loud somewhere, because that's the actual selling point.

Sure — a few observations from this run.

**What worked well.** The phase-gating with `depends_on` and `next_actions` made context loading deterministic — at session start I knew protocols was a sibling of contracts, what to read first, and what porting was waiting on. The evidence-level tagging (`observed fact (file:line)` / `strong inference` / `portability hazard` / `open question`) was more than ceremony — it forced me to decide whether I was claiming a fact, drawing a conclusion, or admitting uncertainty, and that discipline showed up in the deliverable. The append-mode secondary outputs (public-surfaces, runtime-lifecycle, state-and-storage, config-model) let four phases contribute on the same topics without write conflicts or one mega-file.

**Pain points.** The skills themselves are terse — `protocols/SKILL.md` is mostly bullet lists. I leaned heavily on the contracts deliverable as a calibration reference for depth and tone; without that prior output to mimic, the protocols deliverable would have come out thinner. A short "good output looks like" excerpt or a sample line count per section would help. Templates have the same gap — `templates/protocols-and-state.md` is a skeleton with placeholder tables, but the actual deliverable I produced was ~1450 lines. New runs following the template literally would underproduce.

Cross-phase consistency isn't checked. Contracts and protocols both touch the closed-enum dispatcher, the redaction contract, and the SSE grammar; I had to manually keep them aligned. A consistency-pass — even just a subagent that reads two adjacent deliverables and reports drift — would catch where the same claim drifts across phases. Defect IDs as cross-references are brittle for the same reason: downstream phases cite D1.5/D4.7/D5.1 etc. heavily, and if the scan ever re-numbered findings, every cross-ref would silently break. A durable claim ID would be more robust, though more bureaucratic.

`status.yaml` is doing a lot — `current_phase`, `last_updated`, per-phase `status/owner_notes/outputs_present/open_questions`, plus a global `next_actions`. It's brittle: miss a sub-field and the next session has to reverse-engineer intent. The "parallel phase warning" in GUIDE.md is honest about the lock-free reality, but a templated "starting a phase" snippet would lower drift risk. Validation is presence-based, not quality-based — "an event catalog is documented" passes whether the catalog is exhaustive or three lines. A per-criterion calibration ("at least N variants enumerated for each closed enum") or a separate quality-validation subagent run would help.

Append-mode secondary outputs also grow without bound. After 4 phases, public-surfaces.md has overlapping descriptions of the same surfaces in slightly different framings. There's no formal supersession rule — recency wins by convention but it isn't documented. A pre-reimpl-spec "reconcile" pass to fold redundant entries and mark superseded claims would help downstream phases. Relatedly, phase outputs can't *correct* prior phases; they can only add or raise new questions. If protocols discovers the architecture map is wrong about something, the only paths are silent workaround or upward carry-forward. A formal amendment mechanism would handle late discoveries cleanly.

One practical gap: heavy source reading requires subagent delegation, but the framework doesn't mention it. Reading 29 SQL migrations + a 4000-line `protocol.rs` + the v2 schema + the SSE parser + the auth manager would have blown my context window; I delegated to four parallel Explore subagents and ingested structured reports. That's the right move, but a note in GUIDE.md ("for large source bodies, delegate analysis and ingest the structured report") would help less-experienced runs find that pattern.

**Smaller things.** The `scratch/` directory exists but I didn't use it — subagent reports came back inline. If the framework wanted a paper trail of intermediate analysis, scratch/ could have a more prominent role. The GUIDE acknowledges that several guardrails ("don't mark complete on FAIL") rely on the LLM following instructions; pragmatic for now, and the note that a "code-backed implementation should enforce them programmatically" is the right next step.

**One thing worth calling out.** The five pre-flagged items routed defect-scan → contracts → protocols (DD2.1, DD5.3, DD6.1/2, DD5.1, D5.x/DD5.x) had exactly the right shape: contracts pinned the semantics ("what should happen"), protocols pinned the wire shape ("what bytes flow"), and porting will collapse them. That's a workflow that respects a real cognitive distinction, and it's hard to get right. The pre-pass / open-question / carry-forward triad is the part of this framework I'd most want to see other reverse-engineering harnesses copy.

What worked well

Having public-surfaces, runtime-lifecycle, state-and-storage, and config-model accumulate phase-tagged sections gave me a clear way to add new facts without overwriting prior context, and a future session reading any one of those files gets a chronological story instead of a lossy snapshot. #Feedback from an agent running a broad Defect Scan.

Using it on a 91-crate, ~780K-LOC repo for an end-to-end phase surfaces real friction that didn't show up in the architecture phase. Most of this is constructive; the framework's bones are solid.
What worked well
The phase-by-phase separation with explicit depends_on and a single status.yaml source-of-truth is genuinely useful — it survived a phase boundary and a fresh session pickup with no friction. The carry-forward mechanism (architecture → defect-scan) was the single highest-value piece: I started Pass 1 with four pre-targeted hypotheses that turned into four confirmed/refined findings (D4.8, D6.4, D6.5, D4.2). Without that, I'd have spent the first third of the session re-discovering scope. The six-pass split with one SKILL.md file each is the right granularity — it forced category discipline so I didn't conflate concurrency findings with security findings just because they touched the same file. The PASS / PARTIAL / FAIL / PASS WITH GAPS taxonomy with appended validation block is a good forcing function — it makes "I didn't quite finish" a first-class outcome rather than a quality compromise.
What I'd change
Document-as-you-go isn't a first-class workflow. Your project instructions told me to do this because of context limits, but the framework's templates assume you sit down once, fill in the table, and append the validation block at the end. On a repo this large that's not realistic — I had to scaffold the file with placeholder sections, then come back and Edit the placeholders. A template that explicitly supports incremental append (each pass section as an "append-mode" block, the way secondary outputs work) would be honest about how this actually plays out, and would let an LLM checkpoint mid-pass without losing prior findings to a context overflow.
*The action-set switch (fix before porting / port differently / leave behind vs. fix now / track / accept / investigate) is determined by pipeline, but SKILL.md asks the model to "determine which action set to use by checking the pipeline field." That's a coin-flip step in practice. Either the action vocabulary should be unified across pipelines (with one extra column like "porting impact"), or the active pipeline YAML should literally list the allowed action tags so the model copy-pastes from a pinned list.
Severity guidance is thin for security findings. The standard severity ladder ("critical = wrong results in normal use") doesn't map cleanly to "model-trusted-but-fallible code can OOM the host" (D4.2). I ended up assigning medium and footnoting "for a port that wants to harden against compromised models, this is high." A second axis ("trust assumption" or "if the threat model changes to X, severity becomes Y") would make security findings more decision-useful for porting.
The [carry-forward] tag is great but undocumented. It's not in any SKILL.md or template — I picked it up from the architecture phase's prior use and continued the convention. Should be a first-class tag in the schema with a defined lifecycle (raised → confirmed/refuted → closed).
Counts in the summary table are easy to get wrong. I had to fix mine twice — first miscounted the medium total, then forgot to include the accept row in the grand total. A make verify-counts-style sanity check (or a template that derives totals from the rows) would help.
No guidance on "what does 'open question' really mean across phases". The architecture phase logged 10 open questions, all closed by a pre-pass. Defect-scan added new ones — but my "[for follow-up deeper pass]" tag is invented. The framework would benefit from a single open-question taxonomy: defer-to-phase-X, needs-runtime-test, needs-maintainer-decision, out-of-scope-by-policy, etc. Right now downstream phases have to read prose tags and guess.
Validation rule 3 ("findings sorted by severity") is fuzzy on ties and on whether the table itself must be sorted vs. just grouped. I ended up grouping high → medium → low within each pass but not strictly sorting within ties, and called it PASS WITH GAPS. A clearer rule (e.g., "primary key: severity desc; secondary key: finding ID asc") would let validators agree.
The framework assumes one model in one session does one phase. In practice the three reminder-prompts I got mid-pass about "consider using TaskCreate" suggest the host environment has its own opinions about workflow that aren't reflected in GUIDE.md. Some integration note about how TodoWrite-style task tracking interacts with phase progress (they're orthogonal but both want to be source-of-truth) would help.
Smaller things

templates/defect-report.md has only one row per pass table; on a real run you immediately discard it and write your own. The template should either be empty (let the model build the table) or have a row-template comment showing the conventions.
LOG_PARTITION_SIZE_LIMIT_BYTES and similar constants in the codebase that I cited — there's no recommended way to indicate "I read this constant but didn't transcribe its value." A [fact: file:line, value=X] mini-syntax would catch transcription errors.
The "Top Findings" section in the summary asks for "ranked by severity and confidence" but doesn't say how many to list. I picked 10; the template's 1. 2. 3. 4. 5. skeleton implies 5. Worth pinning.

The thing I'd most want next: a programmatic validator that reads the appended validation block, the front-matter (severity/evidence/action), and the row counts, and either passes or fails the file before the model is allowed to mark complete in status.yaml. The Guardrails section in GUIDE.md admits these "rely on the LLM following instructions" — that's the right place for code to take over.
Overall: the framework gave me a workable scaffold for a problem (deep audit of a large unfamiliar codebase) where without it I'd have produced something less structured. The friction points above are mostly the kind you only see by running it through, which is what you asked for.

#Feedback from an agent running a Deep Defect Scan.

 a few observations from running both phases of it on this codebase. I'll group by what worked, what got in the way, and small concrete suggestions.
What worked well
The phase/skill/template separation is the strongest part. Reading GUIDE.md → status.yaml → <phase>/SKILL.md → templates/<phase>.md is a small enough ritual that it's hard to skip, and it makes resuming a phase across sessions cheap. The fact that status.yaml is the single source of truth (and not the report file) means the index never drifts from the artifact. The open_questions carry-forward mechanism between phases is a genuinely good idea — closing four architecture-phase carry-forwards in the broad scan, then closing three broad-scan open questions in the deep pass, gave the work a satisfying audit-trail shape that wouldn't have emerged otherwise.
The pass split for defect-scan (six categories, sequential) was useful as a checklist but I ignored its prescribed ordering. On a 780K-LOC codebase, reading every relevant file six times is wasteful — I read each crate once and collected findings across all six passes simultaneously, then organized by pass at write time. The SKILL.md says "Run these passes sequentially" which actively misled me on the first pass before I switched. Worth softening that to "organize findings by pass; you can collect them in any order."
Things that got in the way
The validation block format conflates two different things — completion-criteria check (mechanical: did you fill in all the columns?) and quality assessment (subjective: are the findings any good?). Criterion 3 ("organized by pass and sorted by severity") in particular is a near-tautology that a well-written report can't fail. None of the criteria would have caught e.g. "you only looked at the headers of every file" or "your severity calls are wildly inconsistent". A real quality bar is hard to encode in a checklist, so maybe that's just an inherent limit, but the current criteria feel like security-theater PASS-stamps rather than a real gate.
The "do not modify" trust-boundary table is good but the file-handling discipline around the report itself is underspecified. The broad scan wrote to defect-report.md; the deep pass needed to extend it without overwriting. There's no convention for "appending a follow-up section" — I invented DD<pass>.<n> IDs and a "Deep Pass" subsection inline, which works but a future session would have to reverse-engineer my choice. A template like templates/defect-report-followup.md plus a documented ID-prefix convention (e.g., "second pass uses D2_<pass>.<n>") would prevent each session from re-inventing this.
The action set vocabulary (fix before porting / port differently / leave behind) is well-chosen but the line between fix before porting and port differently is fuzzier than the SKILL.md admits. Almost every "fix before porting" finding I marked could equally be "port differently" depending on whether the new implementation will mirror the old shape. A short rubric — "fix before porting if the bug is in behavior the new impl will preserve; port differently if the bug is in the implementation choice itself" — would help.
Small concrete suggestions
Add a line to GUIDE.md Context-Budget that says something like "for very large codebases, organize findings by pass but read source by crate/module; you don't have to do six full-codebase reads." This matches what actually has to happen and removes the misleading sequential-pass framing.
The open_questions field in status.yaml is a free-text list. Once you have ~10 of them across phases it gets hard to track which are "needs runtime test", "deferred by scope choice", "carry-forward to phase X", etc. A small structured shape ({id, kind, target_phase, deferred_reason}) would make the followup-pass kickoff prompt I just got from you mechanically constructable.
The pass file for 02-error-handling and the pass file for 04-security-and-trust overlap heavily on "errors that drop secret-bearing data" — DD4.2 (token-refresh body logging) lives equally well in either. The cross-listing convention works but it's ad-hoc. Either explicitly bless cross-listing in the SKILL.md, or carve out a clearer division of labor between the two passes.
Finally, the framework assumes a single-LLM session per phase, but for a 780K-LOC codebase a single deep pass already saturates context. The "if you are running low on context, finish the current section, write a PARTIAL validation, and document what remains" advice in GUIDE.md is correct but the partial-validation block format isn't shown anywhere. I had to extrapolate. A worked example in VALIDATE.md for the partial case would help.
Net: the framework is opinionated enough to be useful and loose enough to bend when the codebase pushes back. The biggest single improvement would be tightening the loop between status.yaml's open_questions and the next session's resumption — that's where the persistent-memory-across-sessions promise pays off, and where small structural tweaks would compound.

#Feedback from an agent working through the porting phase end-to-end.

What worked well. The phase ordering and the depends_on graph created good information flow: by the time I got to porting, contracts had already pre-flagged the security-critical defects as port contracts, protocols had pinned the wire-level invariants, and defect-scan had organized everything by leverage. The carry-forward convention ([carry-forward → defect-scan] in open_questions) preserved context across phases reliably. The four evidence levels (observed fact / strong inference / portability hazard / open question) gave a vocabulary that was actually used consistently. The split between THREAD_LOG.md (cross-session log) and status.yaml (durable progress) is the right shape — they have different audiences and different read patterns. And the "port contract vs current implementation" distinction the contracts phase introduced was the single most useful innovation in the framework — it cleanly separates "what the port must do" from "what the source does today," which is exactly the question a clean-room re-impl needs answered.
What was friction. A few things stood out.
The bundle template doesn't quite fit the porting phase's synthesis role. The template asks for Domain Glossary and Observed Facts vs. Inferred Structure — both genuinely useful in early phases, but by porting they're partially redundant with what's already in architecture and contracts. Meanwhile the template has no slot for the deliverables the porting SKILL actually asks for (per-defect classification, hazard triage, feature-importance refinement). I added them as ad-hoc sections; the next person will too. Tightening the template to match the SKILL would help.
The append-mode secondary outputs accumulate overlap. By the time I reached public-surfaces.md, it had architecture / contracts / protocols / porting sections, each restating parts of the public surface in slightly different framings. The framework has no rule for "when to consolidate vs append" and no de-duplication mechanism. A 5th phase appending into a file that's already 230 lines means reading all four prior sections to avoid restating their facts. A consolidation pass — or a "this section supersedes earlier sections" marker — would make the secondary outputs more usable downstream.
The carry-forward mechanism is push-only. Each phase's open_questions says where the question is being routed, but the destination phase has no "inbox" — it's expected to remember to look. As a fresh agent picking up porting, I had to grep through the prior four phases' open_questions to find what was queued for me. A consolidated inbox: [] field per phase, populated as upstream phases route carry-forwards in, would close that loop.
Validation is structural rather than semantic. "Findings are marked with evidence levels" passes as long as I tag every section, but it wouldn't catch a strong-inference claim mislabeled as observed fact. That's probably acceptable — semantic validation would need a second LLM pass — but the framework should be honest that the validation block is a completeness check, not a correctness check.
The pipeline YAMLs duplicate phase definitions. pipeline-full-with-audit.yaml and pipeline.yaml are mostly the same with one phase removed. If a completion_criteria line changes, both have to update. A composition mechanism (a base pipeline + per-variant skip lists) would be a small change with disproportionate maintenance benefit.
The deliverable file sizes outgrew the practical read-budget. behavioral-contracts.md was 37K tokens — too large for the Read tool's default 25K cap. I read it in chunks. That's fine for a model with a generous context window, but the framework would benefit from per-section size targets and/or an explicit "summary companion" file (behavioral-contracts-summary.md) for downstream phases that only need to skim.
Smaller things. No first-class scope field per phase (the defect-scan phase recorded scope in owner_notes prose; a structured scope: { in: [...], out: [...], deferred: [...] } would be cleaner). The SKILL.md and template files drift apart — they're describing the same thing in two formats. The 4 evidence-level tags are useful early on but feel verbose by the synthesis phases when most assertions are citations.
Net: the framework's bones are good — the phase graph, the port-contract distinction, the secondary-outputs pattern. The friction is mostly in the seams between phases (carry-forward inbox, append vs consolidate, template fit for synthesis) rather than the phases themselves. If I were running it again on a different repo, I'd reach for it as-is and put up with the seams.
