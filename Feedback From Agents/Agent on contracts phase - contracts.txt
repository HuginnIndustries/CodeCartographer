#Feedback from an agent running the contracts phase.

What worked well
The phase-output → secondary-append pattern is the strongest thing in the framework. Having public-surfaces, runtime-lifecycle, state-and-storage, and config-model accumulate phase-tagged sections gave me a clear way to add new facts without overwriting prior context, and a future session reading any one of those files gets a chronological story instead of a lossy snapshot. The architecture phase's "Resolved" subsection (where the prior session went back and answered its own open questions before downstream phases fired) is a nice example of this paying off — I trusted those resolutions.
The defect-scan → contracts handoff worked exactly as designed. Pre-flagging D5.x/DD5.x as "drift the contracts phase must pin down" let me write port-contract rows that are clearly distinct from current implementation behavior. The "what's broken" vs. "what should the port guarantee" split is a real distinction this framework forces you to make, and the output is better for it.
VALIDATE.md's "PARTIAL not PASS when uncertain" rule is good discipline, and the explicit "do not mark complete with FAIL" guardrail is the kind of rule that survives even when the LLM is rushed.
What was awkward
The most-loaded session-context cost is the "required reads" expanding by phase. By contracts, the prerequisites already reach ~100K tokens (architecture-map, defect-report, four secondary outputs, SKILL.md, template). I delegated the deep source probing to a subagent specifically to keep the primary context for synthesis — but the framework doesn't say to do that. A note in GUIDE.md about delegating heavy reads to subagents would help.
The append-mode contract is under-specified. The pipeline YAML says mode: append but doesn't say what to append: another section? A new heading? A delta against prior content? I picked ## Phase: <name> (YYYY-MM-DD) to match the architecture phase's precedent, but a future contributor could legitimately do something different. The template files don't show append-mode examples.
The parallel-phase warning in GUIDE.md is correct but the failure mode is silent — if two sessions update status.yaml concurrently, the second clobbers the first and nothing detects it. A "read modtime, write CAS-style" hint, or even just "run git status .codecarto/workflow/status.yaml before writing", would be a small improvement.
There's a secondary-output target mismatch I noticed: the contracts phase appends to public-surfaces, runtime-lifecycle, state-and-storage, config-model but NOT build-and-deploy, while porting appends to all five. That's reasonable but not documented anywhere — I had to read the pipeline YAML to confirm. A small "secondary-output ownership matrix" table in GUIDE.md showing which phase appends to which file would help.
Skill files vs. templates redundancy. findings/contracts/SKILL.md and templates/behavioral-contracts.md overlap in what they ask for. The skill emphasizes "split by surface, evidence levels, acceptance list" and the template enforces it structurally. I ended up reading both and reconciling. Consolidating one as authoritative and the other as a stub-pointer would reduce ambiguity.
No mechanical schema validator. Several criteria are checkable by code — "every contract row has an Owner field," "every finding has an evidence tag," "the acceptance list cites every pre-flagged defect." A simple linter (regex over the markdown) would catch errors that the LLM's self-validation misses. Today validation is "the LLM grades its own homework," and the rule "do not inflate results" depends on the LLM following that instruction — which it might not.
One actual bug. The status.yaml comment says "If current_phase is set to complete when all phases are done." But the pipeline-full-with-audit YAML has 6 phases with cross-dependencies, and the only way to know which phase to set current_phase to is to traverse phase_order and look at depends_on. The comment makes it sound like the model just has to pick the next pending phase, but with sibling phases (contracts and protocols both depending only on architecture) the rule is genuinely "set to the next phase whose depends_on is satisfied AND that you intend to run next." Worth clarifying.
Suggestion for the next iteration. A THREAD_LOG.md entry template (parallel to the existing output templates in templates/) would standardize what goes into each entry — right now entries vary in length and structure across sessions, which makes the cross-session log less useful for skimming.
Net: the framework is doing real work — it produced a contracts deliverable that I could not have produced freehand without losing structure or skipping the defect-pinning. The friction is mostly around context-budget discipline and a handful of under-specified rules at the boundaries.
