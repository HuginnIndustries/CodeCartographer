#Feedback from an agent running a Deep Defect Scan.

 a few observations from running both phases of it on this codebase. I'll group by what worked, what got in the way, and small concrete suggestions.
What worked well
The phase/skill/template separation is the strongest part. Reading GUIDE.md → status.yaml → <phase>/SKILL.md → templates/<phase>.md is a small enough ritual that it's hard to skip, and it makes resuming a phase across sessions cheap. The fact that status.yaml is the single source of truth (and not the report file) means the index never drifts from the artifact. The open_questions carry-forward mechanism between phases is a genuinely good idea — closing four architecture-phase carry-forwards in the broad scan, then closing three broad-scan open questions in the deep pass, gave the work a satisfying audit-trail shape that wouldn't have emerged otherwise.
The pass split for defect-scan (six categories, sequential) was useful as a checklist but I ignored its prescribed ordering. On a 780K-LOC codebase, reading every relevant file six times is wasteful — I read each crate once and collected findings across all six passes simultaneously, then organized by pass at write time. The SKILL.md says "Run these passes sequentially" which actively misled me on the first pass before I switched. Worth softening that to "organize findings by pass; you can collect them in any order."
Things that got in the way
The validation block format conflates two different things — completion-criteria check (mechanical: did you fill in all the columns?) and quality assessment (subjective: are the findings any good?). Criterion 3 ("organized by pass and sorted by severity") in particular is a near-tautology that a well-written report can't fail. None of the criteria would have caught e.g. "you only looked at the headers of every file" or "your severity calls are wildly inconsistent". A real quality bar is hard to encode in a checklist, so maybe that's just an inherent limit, but the current criteria feel like security-theater PASS-stamps rather than a real gate.
The "do not modify" trust-boundary table is good but the file-handling discipline around the report itself is underspecified. The broad scan wrote to defect-report.md; the deep pass needed to extend it without overwriting. There's no convention for "appending a follow-up section" — I invented DD<pass>.<n> IDs and a "Deep Pass" subsection inline, which works but a future session would have to reverse-engineer my choice. A template like templates/defect-report-followup.md plus a documented ID-prefix convention (e.g., "second pass uses D2_<pass>.<n>") would prevent each session from re-inventing this.
The action set vocabulary (fix before porting / port differently / leave behind) is well-chosen but the line between fix before porting and port differently is fuzzier than the SKILL.md admits. Almost every "fix before porting" finding I marked could equally be "port differently" depending on whether the new implementation will mirror the old shape. A short rubric — "fix before porting if the bug is in behavior the new impl will preserve; port differently if the bug is in the implementation choice itself" — would help.
Small concrete suggestions
Add a line to GUIDE.md Context-Budget that says something like "for very large codebases, organize findings by pass but read source by crate/module; you don't have to do six full-codebase reads." This matches what actually has to happen and removes the misleading sequential-pass framing.
The open_questions field in status.yaml is a free-text list. Once you have ~10 of them across phases it gets hard to track which are "needs runtime test", "deferred by scope choice", "carry-forward to phase X", etc. A small structured shape ({id, kind, target_phase, deferred_reason}) would make the followup-pass kickoff prompt I just got from you mechanically constructable.
The pass file for 02-error-handling and the pass file for 04-security-and-trust overlap heavily on "errors that drop secret-bearing data" — DD4.2 (token-refresh body logging) lives equally well in either. The cross-listing convention works but it's ad-hoc. Either explicitly bless cross-listing in the SKILL.md, or carve out a clearer division of labor between the two passes.
Finally, the framework assumes a single-LLM session per phase, but for a 780K-LOC codebase a single deep pass already saturates context. The "if you are running low on context, finish the current section, write a PARTIAL validation, and document what remains" advice in GUIDE.md is correct but the partial-validation block format isn't shown anywhere. I had to extrapolate. A worked example in VALIDATE.md for the partial case would help.
Net: the framework is opinionated enough to be useful and loose enough to bend when the codebase pushes back. The biggest single improvement would be tightening the loop between status.yaml's open_questions and the next session's resumption — that's where the persistent-memory-across-sessions promise pays off, and where small structural tweaks would compound.
