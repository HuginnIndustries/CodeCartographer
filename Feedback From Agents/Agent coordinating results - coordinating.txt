#Feedback from an agent coordinating the results from other strings.

Yes, I have substantive feedback. The framework is good — the pipeline went six phases without procedural drag, and the deliverables are usable artifacts. But there are real gaps, and the parts that work best are not always the parts that get the most attention in the docs.
What works (and would be missed if removed)
The validation gate. Forcing PASS / PASS WITH GAPS / FAIL with a criterion-by-criterion citation table at the bottom of every primary output is the single most disciplining feature. Without it I'd have shipped softer outputs. Re-validation after the open-question pre-pass worked cleanly. Don't change this.
Append-mode secondary outputs. This is the framework's quiet superpower. Reading state-and-storage.md after the pipeline closes, you can watch the same SQLite story accumulate ("29 migrations" → "logs moved to dedicated DB" → "logs at logs_2.sqlite, separate pool, 10-day retention" → "archive-by-default migration policy"). The dated phase sections create a record of how understanding grew, not just what's known. Most frameworks throw away that history.
Pipeline variants. Five is the right number. The full-with-audit / full / lite / defect-scan-only / architecture-only split actually maps to real use cases. The user picking a variant up front, with the YAML enforcing the phase set, kept scope honest.
Trust boundaries (read-only vs writable). The table at the top of GUIDE.md is small but load-bearing. Made it impossible to accidentally modify a SKILL.md or pipeline YAML. Should be the first thing every framework defines.
Skill files with structured prompts. The architecture SKILL.md's "Test for common structural patterns" list (shared provider layer, agent loop, multiple delivery surfaces, plugin architecture, etc.) actually changed how I clustered. Without that nudge I might have written a flat package list. Templates removed the blank-page problem; SKILLs removed the wrong-shape problem.
What had friction (real, not nitpicks)
open_questions is one field doing two jobs. Real unknowns and "deferred to later phase" both end up there, distinguishable only by whether I added a [carry-forward → defect-scan] tag I had to invent. Should be two fields: open_questions (still genuinely unknown) and carry_forward (resolved by the framework's later phases, with explicit phase target). Schema mismatch caused real friction at every phase handoff.
Phases overlap in practice; the framework presumes clean handoffs. Defect-scan resolved architecture questions. Contracts pinned defect findings as port contracts. Protocols pinned contracts at wire level. The strict phase boundary worked, but the receiving phase had to know to look back for resolved items, and there's no machinery for that. A "previously resolved" footer in each output would help; better still, a resolutions/ directory the next phase reads automatically.
No "strategic alignment" hook before the synthesis phase. Our discussion before the reimpl-spec — provider-agnostic, target stack, naming — produced inputs the spec actually needed. Without it the spec would have been generic. The framework has no place for that conversation. The reimpl-spec template defaults to "any port to any stack," which is the wrong tool when the user has specific opinions. A pre-spec strategic-alignment template (or just an explicit prompt: "Have you locked target stack, scope cuts, and project identity?") would have caught this.
The relationship between primary and secondary outputs is undocumented. I invented the rule "summaries in primary, details in secondary" because nothing in GUIDE.md specifies it. The architecture-map's Public Surfaces, Runtime Lifecycle, Build and Packaging sections directly overlap with the secondary outputs of the same names. Without a rule, those duplicate or contradict. Should be: primary owns the map and the load-bearing claims; secondaries own the catalog-level detail. Spell it out.
Subagent delegation isn't blessed. I leaned heavily on subagents for the 91-crate dependency walk and the Pi-mono comparison. The framework is silent on this. For codebases over some threshold (~50 source files? ~100K LOC?), explicit guidance on what to delegate would prevent the obvious failure mode of "burn primary context on extraction work." A two-line note in GUIDE.md would do it.
The reimpl-spec template defaults to generic-port mode. The user wanting an opinionated, named, target-specific spec was the most informative case I encountered, and the template offered no help. A second template variant — "specific named port with locked target stack" — would have skipped the strategic-alignment improvisation we did. Pi-mono's spec was already in this mode (named project, named modules, named primitives), so the pattern is proven.
Defect-scan didn't naturally fit a phase boundary. Two-pass (broad → deep) was a clean pattern that emerged from the conversation, not the framework. The defect report ended up with both passes appended into one file, which works, but the framework presumes "one pass = one phase output." A defect-pass-N append discipline (like secondary outputs) would have been more honest about how defect work actually plays out.
What I'd actually change
If you do another revision, in priority order:

Split open_questions into open_questions + carry_forward with explicit phase targets. Cheapest change, highest leverage.
Add a "primary vs secondary outputs" section to GUIDE.md. Two paragraphs. Specifies the summary-vs-detail rule.
Add an optional pre-synthesis strategic-alignment phase (or at minimum, a checklist the GUIDE prompts before reimpl-spec): target stack, project identity, scope cuts, named primitives. The reimpl-spec template gets a variant for "specific named port."
Add subagent guidance for large codebases. One paragraph. "Delegate dependency mapping, file inventories, and cross-document comparisons to subagents and cite their scratch artifacts."
Bless the multi-pass append pattern for defect-scan. Same model as secondary outputs: pass-N gets a dated section, no overwrites.
Add a resolutions/ mechanic so later phases can see what earlier phases resolved. Either a directory or an explicit footer in each primary output.

What I would not change: the validation gate, the append-mode secondary outputs, the trust boundaries, the pipeline variants, the skill files, the evidence-level discipline. Those are the load-bearing parts and they earned their weight.
The framework's biggest strength, which the docs underplay: it makes honest output the default. The validation block can't be skipped, evidence levels can't be left blank, the open-questions field is in your face at every status update. Most agent frameworks let you ship slop. This one doesn't. Worth saying out loud somewhere, because that's the actual selling point.
