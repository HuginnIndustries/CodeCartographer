#Feedback from an agent running the reimplementation spec

Yes, several things worth flagging. The phased pipeline is genuinely good cognitive scaffolding — having required_reads enforced at each phase, plus validation blocks that force me to self-check against completion_criteria, kept me honest in ways I'd skip on my own. The carry-forward routing in open_questions (e.g., [carry-forward → contracts] tags routing items to the next phase that can actually pin them down) is elegant — it lets each phase own only what it can responsibly close. And the JSONL-style separation of THREAD_LOG.md (cross-session pointer) from findings/ (durable artifacts) from status.yaml (single source of truth) is a clean split that I'd want to copy elsewhere.
Friction worth naming:
The reimplementation-spec SKILL.md pushes "language-agnostic" as the default frame, but my actual task today was the opposite — an opinionated TS-on-Bun spec for a known clean-room re-implementation. The framework didn't anticipate that mode. The template's section list (External Dependencies as replace/wrap/emulate/postpone, etc.) is awkward when you've pre-committed to a stack — most of the table degenerates into "wrap the standard library." A dual-mode skill (mode: language-agnostic vs mode: opinionated) with different templates would land cleanly.
Primary outputs grew large enough to be hard to re-read in one shot. The porting bundle hit ~30K tokens and exceeded the Read tool's per-call limit, forcing chunked reads. Phases that consume earlier deliverables would benefit from a pre-condensed <phase>-summary.md companion file (maybe 1–2K tokens) that downstream phases read instead of the full document. The full bundle stays as the source of truth, but the summary is what the next phase actually loads.
Cross-CodeCartographer references are unsupported. The user's brief told me to cite Pi-mono's spec by named heading; there's no formal mechanism in the framework for "this analysis is informed by another CodeCartographer-shaped repo." A references field in status.yaml pointing at other CodeCartographer workspaces (with citation conventions) would close that loop and make multi-repo synthesis a first-class operation.
The architecture-phase context-budget guidance is too soft. For 91-crate / 780K-LOC source like codex, "estimate how much you need to read" doesn't give me a technique. Each SKILL.md could carry an explicit depth-scaling hint (e.g., "for repos >100K LOC, read manifests + entrypoints + one representative module per layer; defer the rest until contracts/protocols ask"), which would force more disciplined first reads.
Validation rubric is binary about structural completeness but soft about coverage depth. For the reimpl-spec, I could always have added more acceptance scenarios — but the criterion just says "are included." Distinguishing "structural completeness" (PASS/FAIL) from "coverage depth" (a 1-5 score with rubric) would let downstream consumers know whether a passing phase is thin or thorough.
None of these are blocking — I got the work done — but they're places where the framework could carry more weight that's currently on the operator.
