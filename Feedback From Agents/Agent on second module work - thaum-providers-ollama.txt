Feedback from a model-work session implementing the second Thaumaturge
module (`thaum-providers-ollama`) against the codecarto-produced
reimplementation spec, the round-2 captured fixtures, and the
`thaum-protocol` package from the previous module-work session.

Date: 2026-05-02
Model: Claude (anthropic)
Session: module-2 (`thaum-providers-ollama`) — second-ever code-producing
session against this codecarto bundle.


WHAT WORKED REALLY WELL
=======================

1. Fixtures-as-vendored-stable-artifacts.

   The round-2 spike captured exact wire bytes for four Ollama scenarios
   (text-only, length-truncated, thinking-channel, error-bad-model) plus
   per-fixture metadata (httpStatus, contentType, body bytes). The session
   prompt told me to copy them into `tests/fixtures/` and check them in
   rather than reference by absolute path. This was the right call: my
   replay tests now produce the exact NormalizedAssistantEvent sequence
   per fixture, and a future round-3 capture is a deliberate refresh
   rather than a flaky live link. The "name + raw + expectedEvents"
   shape pinned in the prompt was the right granularity.

2. Δ-numbered deltas with traceability suffixes.

   The spec's revisions section uses a discipline of "Δ-N | source | text"
   per row, and applied edits in the body carry inline citations like
   `[revised per spike-N-slug.md §Δ-N]`. The round-2 layer adds verification
   suffixes — `[verified-on-ollama spike-8 §Δ-N]` vs
   `[provisional-on-opencode-zen — round-3 pending]`. As an implementer I
   could SEE which spec rules were verified-on-real-Ollama (and so could
   write tests with confidence) vs PROVISIONAL (and so should mark tests
   provisional or skip them). This is genuinely a load-bearing convention,
   not just documentation hygiene.

3. The "discipline" section in the session prompt.

   - "Honor the spec's Origin column literally" — the Synthesized vs
     Translated distinction made the channel-state-machine design
     obvious (anything Synthesized is the adapter's responsibility).
   - "Pre-stream errors are first-class" — pinned a path I might have
     conflated with in-stream errors.
   - "No engine logic" — kept me from accidentally implementing
     conversation-history merging or sandbox logic in the adapter.
   - "No abstract Provider machinery" — explicit "don't write a
     BaseProvider". This is the kind of guidance that's easy for the model
     to ignore without being told. Saying it explicitly was effective.
   - "Tests cite the spec" — every test file's header cites the §s/Δs
     it verifies, which mirrors the discipline in `thaum-protocol`. Made
     the test files self-documenting.

4. status.yaml as a handoff baton.

   The `next_actions` list ended exactly where I needed to start. I
   could read it, see "thaum-providers/ollama end-to-end against the
   round-2 captures at .../ollama-real-fixtures/", and know: which
   fixtures, which spec deltas, which tests-tagged-provisional. The
   `current_phase: complete` discipline (module work doesn't reopen
   phases) keeps the workflow concept clean — module work is post-
   pipeline, not a new pipeline.

5. THREAD_LOG.md template.

   The "thread goal / files analyzed / durable output / decisions made
   beyond prompt / verification / next session" structure is a really
   good closeout shape. The "decisions made beyond prompt" section in
   particular is high-signal — when the next session reads this entry
   they get an honest record of where the implementer made a judgment
   call, not just a sanitized summary.

6. The spec → tests → behavior chain is end-to-end.

   The spec says "adapter MUST synthesize textEnd before non-text events"
   (Δ-8); the test header says "per spec §Δ-8"; the test asserts the
   exact textEnd-then-done sequence; the implementation has a
   `#closeOpenChannel()` method with a comment citing the same §. Reading
   any one of the three lets you find the other two.


SOME FRICTION
=============

1. The reimplementation-spec.md file in this session was 237 lines.

   The previous session's THREAD_LOG entry (and the `outputs_present`
   in status.yaml) reference a ~1050-line spec. My on-disk copy stops
   mid-sentence in the §thaum-state row of the conceptual model. I ended
   up reconstructing context from the round-1 + round-2 deltas tables and
   the prompt itself, rather than from the canonical §Provider boundary
   and §Required Behaviors sections (which were apparently in the fuller
   version).

   This worked OK because the prompt is comprehensive and the deltas are
   self-contained, but it suggests two things:
   (a) the canonical spec file should be the single source of truth for
       "what is the contract," not the union of the spec body + the
       deltas tables + the session prompt + the THREAD_LOG entry;
   (b) some hygiene that prevents the spec file from getting truncated
       in transit (encoding issues? bad merge? the long-line-pattern in
       this codebase looks fragile to certain editors).

   Concrete suggestion: add a "spec self-check" gate that fails CI if
   the spec file is missing required H2/H3 headings (System Summary,
   Conceptual Module Model, Required Behaviors, Protocols and Persisted
   State, External Dependencies, Host Preconditions, Portability Hazards,
   Implementation Sequence, Acceptance Scenarios, Deliberate Non-Goals,
   Known Unknowns, Spike List, Validation, Backlog).

2. The `next_actions` list scaling.

   By the time my entry was the latest, `next_actions` had 6 long bullets
   (some reading like mini-essays). It's still readable but it's not a
   "list of next actions" any more — it's more of a rolling log of "what
   modules have been done, what's next, what's blocked on what". A
   future cleanup might want to split this into:
     completed_modules: [...]
     next_module: { ... }
     blocked_modules: [...]
     conformance_gates: [...]
   so that an LLM (or a human) doesn't have to skim 600 words of bullets
   to find what to do.

3. Spec rule conflict — resolution went to the prompt, not the spec.

   The spec says: "unknown done_reason → done(stop) plus a Warning
   { kind2: 'ollama_unknown_done_reason' }". The session prompt says:
   "unknown/missing done_reason → 'error' (defensive default)". I went
   with the prompt because (a) it's the contract for this session, and
   (b) Provider.stream emits NormalizedAssistantEvent only — no Warning
   channel from a provider adapter — so the spec's Warning emission would
   need an Engine layer that doesn't exist yet.

   This is fine, but it surfaces a question: when the next session reads
   the spec, will they re-decide? The deviation should probably be
   recorded back into the spec's §Backlog or §Known Unknowns so the next
   reader doesn't relitigate.

   Suggestion: when an implementer makes a "decision beyond prompt" that
   contradicts the spec, the closeout ritual should optionally include a
   spec annotation (`[implemented as 'error' per session 2026-05-02 — see
   THREAD_LOG]`) so the spec stays the single source of truth for
   ground-truth contracts.

4. Verbatim-citation discipline is hard to enforce.

   The session prompt says "verbatim spec citations in code." I cited
   spec sections by name but didn't paste verbatim text into doc-comments
   for every behavior. The test files cite §s and Δs at the header, which
   is good, but a stricter version would require, e.g., `// per spec
   §Provider boundary normative rule 6: "the adapter MUST detect the
   non-SSE path and emit a synthesized..."`. There's a tradeoff here —
   verbatim citations bloat the source — but a more discoverable convention
   would help. Maybe "verbatim quote at the function-level docstring;
   slug-citation at the line-level."

5. The `status.yaml.last_updated` field had to be manually advanced.

   I edited it from "2026-05-02" to "2026-05-02  # thaum-providers-ollama
   scaffolded" — same date, but a tracker comment. A more rigorous
   approach would key the date to the commit / module rather than to the
   YAML field. No big deal.

6. Codex spec mount vs Thaumaturge mount asymmetry (environment-specific).

   This is environment, not codecarto, but worth flagging: the codex
   workspace mount under bash returned stale views of files I'd just
   edited via the host file tools (the codex mount cached a version from
   ~14:11; the host had ~15:08). The Thaumaturge mount didn't have this
   problem. I worked around it by using Read instead of bash to verify
   the spec/THREAD_LOG/status.yaml state.

   Codecarto's discipline of "the spec file is the source of truth" is
   the right one — if I'd been in the habit of reading the spec via
   bash I'd have been working from a stale copy.


WHAT MIGHT HELP THE NEXT MODULE-WORK SESSION
============================================

1. A compact "spec self-test" checklist at the bottom of the spec — a
   list of the sections that MUST be present and the conventions they
   MUST observe (e.g., "every Required Behavior must cite a spec § and a
   defect ID"; "every translation table must have an Origin column"). A
   `bun run spec:check` that runs against the markdown would prevent
   silent truncation regressions.

2. A `tests/CONVENTIONS.md` per module that pins the test-header citation
   format so adapters across packages converge on the same shape. I
   inferred the shape from the existing thaum-protocol tests; it'd be
   slightly more durable to spell it out.

3. A rule in the closeout ritual: "if you made a decision that diverges
   from the spec, append a one-line annotation to the spec's §Backlog
   row so the next reader doesn't relitigate."

4. A `next_actions` schema (see point 2 above) — the rolling-log shape is
   not scaling to 6+ modules.

5. Maybe a `.codecarto/MODULES.md` index that lists each module's
   package name, status, last commit, last test count, last gate-green
   timestamp. Just a tabular at-a-glance view. Today this is reconstructed
   from THREAD_LOG entries each session.


OVERALL
=======

The codecarto framework scales smoothly from "let's reverse-engineer
this Rust monorepo" through "let's run two rounds of pre-implementation
spikes" through "let's actually start writing modules." The spec is the
load-bearing artifact; the deltas are how empirical reality folds back
into the spec; the THREAD_LOG is the institutional memory; the status.yaml
is the handoff baton. Each piece earns its keep.

The pre-implementation spike rounds were particularly valuable. Without
the round-2 captured Ollama bytes I would have written my replay tests
against my best guess at the wire format, and gotten it wrong in subtle
ways (Δ-32's string-valued vs nested error body shape; Δ-33's empty-
string-not-undefined). The fixture-replay-test pattern (vendored-stable-
captures + per-event-sequence assertion) made the spec assertions
literally testable rather than asserted-only.

The work tracking discipline (status.yaml `next_actions` + THREAD_LOG
session entries + verification-suffixed citations) is what made it
possible for me to land a 27-file, 158-test module in one session
without re-deriving anything the previous session(s) figured out.

If I had to summarize the framework's value in one sentence: it produces
a spec that you can implement against test-by-test, where every test
header points back to a spec rule and every spec rule points forward to
a piece of empirical evidence (or honestly admits it doesn't have any
yet). That's a high bar for any spec format and codecarto clears it.
