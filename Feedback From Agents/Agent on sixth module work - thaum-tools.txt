WHAT STRUGGLED
--------------

1. FILE-SYSTEM SYNC LAG (real, lost ~30 minutes).
   The bash mount is lazy: writes via the file tools (Edit/Write) showed
   truncated views in bash for 5-15 seconds. When I appended via bash to
   what I thought was the current content, I appended to a stale truncated
   view, producing garbled files (last byte of em-dash truncated, NUL
   bytes appended, doubled function bodies). The boilerplate warning in
   the prompt was accurate; I'd add concrete mitigations to the warning:
     - For files >100 lines, prefer FULL Write tool overwrites over many
       small Edits (reduces sync race surface).
     - When you must shell-edit, use a Python heredoc that writes the
       full file in one syscall (rather than `cat >> file`). Python
       writes are faster to sync than bash >> appends.
     - After ANY edit, sleep 3-5 seconds then `wc -l && tail -3` before
       running tools that read the file (tsc, oxlint, bun test).
     - When `tail -X` shows truncated content, do NOT append — re-read
       via the Read tool and re-Write the full file.

2. EVENT TIMING IN INTEGRATION TESTS.
   The engine fires `taskComplete` per TURN, not per task. My round-trip
   test initially broke its event consumer on the FIRST taskComplete,
   missing all turn-2 events. Spec/protocol docs are correct (multi-turn
   = multi taskStarted+taskComplete), but I'd flag in §thaum-engine the
   per-turn-vs-per-task semantics and add a "consuming events from a
   multi-turn task" code-example block. (Adding this proposal to status.
   yaml as `OQ-tools-2`.)

3. TOOLS SEAM SHAPE DIVERGENCE.
   The engine's ToolsSeam.execute returns ToolExecutionResult ({type:"ok"|
   "error"}), while the spec's per-tool returns Result<Outcome, ToolResult
   Error>. The mapping is intentional (engine wants a flat shape; tool
   layer wants typed errors), and I kept ToolsSeamImpl as the projector
   between them — but the spec doesn't explicitly describe this projection.
   A short note in §thaum-tools "Public outputs" naming the projection
   ("Result<TOk,ToolResultError> at the tool layer; flattened to
   ToolExecutionResult at the engine seam") would help future readers.

4. SPEC vs PROMPT TOOL INVENTORY.
   The spec lists codex's tool inventory (local_shell/apply_patch/etc.)
   as the §thaum-tools "Responsibility"; the prompt scoped this session
   to a Pi-mono-aligned minimum (read/write/edit/bash). I diverged
   deliberately and recorded as D217 + Δ-38 (pending spec revision). The
   orchestrator should resolve before the next implementing session that
   needs to reason about the inventory.

PROPOSED FRAMEWORK CHANGES
--------------------------

1. ADD A SECTION TO closeout-template.md FOR "VERIFIED CONVENTION
   APPLICATIONS." A bullet list confirming which CONVENTIONS.md entries
   were applied with specific code citations. This would let the
   orchestrator track convention drift and confirm conventions remain
   load-bearing rather than aspirational.

2. ADD A "FRAMEWORK FRICTION" CATEGORY TO THE FEEDBACK FILE FRONT-MATTER.
   Right now feedback files are free-form; a structured top section with
   "what worked / what struggled / proposed changes" makes them more
   merge-able into a future framework-revision pass.

3. THE BOILERPLATE FS-SYNC WARNING SHOULD INCLUDE CONCRETE MITIGATIONS.
   The current wording ("prefer full-file overwrites over many small
   edits") helps but doesn't tell me what to do when the bash mount IS
   stale. Adding the Python-heredoc pattern + the sleep-then-wc verify
   loop would have saved cycles in this session.

4. PROMOTE C13 (DEFENSE-IN-DEPTH INJECTION SLOTS THAT THROW) TO
   CONVENTIONS.md WHEN A THIRD MODULE REACHES FOR IT. thaum-tools'
   ProcessSpawner is the first instance; thaum-exec-policy or thaum-hooks
   may want similar.

5. PROMOTE C14 (TOOLCHAIN SEAM INTERFACES GAIN OPTIONAL CAPABILITY METHODS)
   TO CONVENTIONS.md WHEN A SECOND SEAM EXTENSION USES THE SAME PATTERN.
   ToolsSeam.toolDefinitions?() is the first; HooksSeam may want a
   similar optional capability method.
