#Feedback from an agent running the protocols phase.

Sure — a few observations from this run.

**What worked well.** The phase-gating with `depends_on` and `next_actions` made context loading deterministic — at session start I knew protocols was a sibling of contracts, what to read first, and what porting was waiting on. The carry-forward routing between phases is the strongest piece of the framework: contracts deferred V8 per-tool schemas and hook payload schemas to protocols with explicit handoff text in `open_questions`, so I knew exactly what I owed the next phase and what was owed to me. The evidence-level tagging (`observed fact (file:line)` / `strong inference` / `portability hazard` / `open question`) was more than ceremony — it forced me to decide whether I was claiming a fact, drawing a conclusion, or admitting uncertainty, and that discipline showed up in the deliverable. The append-mode secondary outputs (public-surfaces, runtime-lifecycle, state-and-storage, config-model) let four phases contribute on the same topics without write conflicts or one mega-file.

**Pain points.** The skills themselves are terse — `protocols/SKILL.md` is mostly bullet lists. I leaned heavily on the contracts deliverable as a calibration reference for depth and tone; without that prior output to mimic, the protocols deliverable would have come out thinner. A short "good output looks like" excerpt or a sample line count per section would help. Templates have the same gap — `templates/protocols-and-state.md` is a skeleton with placeholder tables, but the actual deliverable I produced was ~1450 lines. New runs following the template literally would underproduce.

Cross-phase consistency isn't checked. Contracts and protocols both touch the closed-enum dispatcher, the redaction contract, and the SSE grammar; I had to manually keep them aligned. A consistency-pass — even just a subagent that reads two adjacent deliverables and reports drift — would catch where the same claim drifts across phases. Defect IDs as cross-references are brittle for the same reason: downstream phases cite D1.5/D4.7/D5.1 etc. heavily, and if the scan ever re-numbered findings, every cross-ref would silently break. A durable claim ID would be more robust, though more bureaucratic.

`status.yaml` is doing a lot — `current_phase`, `last_updated`, per-phase `status/owner_notes/outputs_present/open_questions`, plus a global `next_actions`. It's brittle: miss a sub-field and the next session has to reverse-engineer intent. The "parallel phase warning" in GUIDE.md is honest about the lock-free reality, but a templated "starting a phase" snippet would lower drift risk. Validation is presence-based, not quality-based — "an event catalog is documented" passes whether the catalog is exhaustive or three lines. A per-criterion calibration ("at least N variants enumerated for each closed enum") or a separate quality-validation subagent run would help.

Append-mode secondary outputs also grow without bound. After 4 phases, public-surfaces.md has overlapping descriptions of the same surfaces in slightly different framings. There's no formal supersession rule — recency wins by convention but it isn't documented. A pre-reimpl-spec "reconcile" pass to fold redundant entries and mark superseded claims would help downstream phases. Relatedly, phase outputs can't *correct* prior phases; they can only add or raise new questions. If protocols discovers the architecture map is wrong about something, the only paths are silent workaround or upward carry-forward. A formal amendment mechanism would handle late discoveries cleanly.

One practical gap: heavy source reading requires subagent delegation, but the framework doesn't mention it. Reading 29 SQL migrations + a 4000-line `protocol.rs` + the v2 schema + the SSE parser + the auth manager would have blown my context window; I delegated to four parallel Explore subagents and ingested structured reports. That's the right move, but a note in GUIDE.md ("for large source bodies, delegate analysis and ingest the structured report") would help less-experienced runs find that pattern.

**Smaller things.** The `scratch/` directory exists but I didn't use it — subagent reports came back inline. If the framework wanted a paper trail of intermediate analysis, scratch/ could have a more prominent role. The GUIDE acknowledges that several guardrails ("don't mark complete on FAIL") rely on the LLM following instructions; pragmatic for now, and the note that a "code-backed implementation should enforce them programmatically" is the right next step.

**One thing worth calling out.** The five pre-flagged items routed defect-scan → contracts → protocols (DD2.1, DD5.3, DD6.1/2, DD5.1, D5.x/DD5.x) had exactly the right shape: contracts pinned the semantics ("what should happen"), protocols pinned the wire shape ("what bytes flow"), and porting will collapse them. That's a workflow that respects a real cognitive distinction, and it's hard to get right. The pre-pass / open-question / carry-forward triad is the part of this framework I'd most want to see other reverse-engineering harnesses copy.
