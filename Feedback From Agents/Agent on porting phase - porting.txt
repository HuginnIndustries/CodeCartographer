#Feedback from an agent working through the porting phase end-to-end.

What worked well. The phase ordering and the depends_on graph created good information flow: by the time I got to porting, contracts had already pre-flagged the security-critical defects as port contracts, protocols had pinned the wire-level invariants, and defect-scan had organized everything by leverage. The carry-forward convention ([carry-forward → defect-scan] in open_questions) preserved context across phases reliably. The four evidence levels (observed fact / strong inference / portability hazard / open question) gave a vocabulary that was actually used consistently. The split between THREAD_LOG.md (cross-session log) and status.yaml (durable progress) is the right shape — they have different audiences and different read patterns. And the "port contract vs current implementation" distinction the contracts phase introduced was the single most useful innovation in the framework — it cleanly separates "what the port must do" from "what the source does today," which is exactly the question a clean-room re-impl needs answered.
What was friction. A few things stood out.
The bundle template doesn't quite fit the porting phase's synthesis role. The template asks for Domain Glossary and Observed Facts vs. Inferred Structure — both genuinely useful in early phases, but by porting they're partially redundant with what's already in architecture and contracts. Meanwhile the template has no slot for the deliverables the porting SKILL actually asks for (per-defect classification, hazard triage, feature-importance refinement). I added them as ad-hoc sections; the next person will too. Tightening the template to match the SKILL would help.
The append-mode secondary outputs accumulate overlap. By the time I reached public-surfaces.md, it had architecture / contracts / protocols / porting sections, each restating parts of the public surface in slightly different framings. The framework has no rule for "when to consolidate vs append" and no de-duplication mechanism. A 5th phase appending into a file that's already 230 lines means reading all four prior sections to avoid restating their facts. A consolidation pass — or a "this section supersedes earlier sections" marker — would make the secondary outputs more usable downstream.
The carry-forward mechanism is push-only. Each phase's open_questions says where the question is being routed, but the destination phase has no "inbox" — it's expected to remember to look. As a fresh agent picking up porting, I had to grep through the prior four phases' open_questions to find what was queued for me. A consolidated inbox: [] field per phase, populated as upstream phases route carry-forwards in, would close that loop.
Validation is structural rather than semantic. "Findings are marked with evidence levels" passes as long as I tag every section, but it wouldn't catch a strong-inference claim mislabeled as observed fact. That's probably acceptable — semantic validation would need a second LLM pass — but the framework should be honest that the validation block is a completeness check, not a correctness check.
The pipeline YAMLs duplicate phase definitions. pipeline-full-with-audit.yaml and pipeline.yaml are mostly the same with one phase removed. If a completion_criteria line changes, both have to update. A composition mechanism (a base pipeline + per-variant skip lists) would be a small change with disproportionate maintenance benefit.
The deliverable file sizes outgrew the practical read-budget. behavioral-contracts.md was 37K tokens — too large for the Read tool's default 25K cap. I read it in chunks. That's fine for a model with a generous context window, but the framework would benefit from per-section size targets and/or an explicit "summary companion" file (behavioral-contracts-summary.md) for downstream phases that only need to skim.
Smaller things. No first-class scope field per phase (the defect-scan phase recorded scope in owner_notes prose; a structured scope: { in: [...], out: [...], deferred: [...] } would be cleaner). The SKILL.md and template files drift apart — they're describing the same thing in two formats. The 4 evidence-level tags are useful early on but feel verbose by the synthesis phases when most assertions are citations.
Net: the framework's bones are good — the phase graph, the port-contract distinction, the secondary-outputs pattern. The friction is mostly in the seams between phases (carry-forward inbox, append vs consolidate, template fit for synthesis) rather than the phases themselves. If I were running it again on a different repo, I'd reach for it as-is and put up with the seams.
