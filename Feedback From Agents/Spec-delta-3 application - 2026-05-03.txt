Framework feedback — round-3 spec-delta application — 2026-05-03
Author: Claude (Cowork mode), running the apply-spec-deltas SKILL on its first real run
Project: Thaumaturge reimplementation (codex workspace)

CONTEXT
The 2026-05-02 framework-feedback pass introduced (among other things) the apply-spec-deltas
SKILL — a structured workflow for applying triaged spec deltas after the pipeline has produced
a complete reimplementation-spec. Round-1 and round-2 spec-revision passes pre-existed the
SKILL and had ad-hoc shapes; round-3 is the SKILL's first real run, with three deltas (Δ-36
from D501, Δ-37 from D502, Δ-38 from a closeout open-question) raised by the first six
implementing module sessions. Round-3 applied two and DEFERed one. This file is the high-
signal framework feedback from that first run.

WHAT WORKED

1. SKILL posture: triage-not-rubber-stamp.
   The single rule of the SKILL ("don't apply deltas verbatim without thinking") landed hard in
   practice: Δ-36's literal proposal in D501 was "map to 'error'" but the application surfaced
   that mirroring the existing in-stream error pattern (error event + done(error)) was a better
   spec-shape, and that decision was captured as a "decision-beyond-prompt" in the closeout.
   The four-bucket matrix (APPLY/CLARIFY/DEFER/REJECT) gave the session a clear vocabulary;
   "any delta you can't decisively bucket should default to DEFER" was an invitation to be
   honest about Δ-38 rather than forcing a half-baked APPLY.

2. Validation-must-not-degrade rule.
   The SKILL's instruction "if the validation block degrades, fix the spec body, do NOT soften
   the validation criteria" worked as a forcing function. Round-3 updated criteria 2/3/4/5
   evidence text to mention the round-3 changes, but the criteria themselves and the PASS
   determinations were preserved. No criterion was dropped, reworded, or weakened.

3. Citation discipline.
   Every applied delta got at least one inline `[revised per ...]` marker in the body, in
   addition to the §Round 3 Revisions subsection summary. Future readers can grep for round-3
   citations to trace what changed and why. (Caveat in §FRICTION below: the canonical citation
   form needed refinement.)

4. Post-pipeline-not-phase-status posture.
   The SKILL says "current_phase stays `complete`. The spec is updated in place; no phase
   status changes." Round-3 honored this: status.yaml's phase didn't change; only
   last_updated and pending_deltas/backlog_carry_forward were touched. Clean.

5. Closeout-template mapping.
   The SKILL's Step 7 closeout instructions plus the existing `templates/closeout-template.md`
   composed cleanly. Decisions Beyond Prompt, Framework Feedback, Files Touched, and Next
   Session Pointer all had natural homes. The template's optional sections (Proposed
   Conventions, Open Questions Left Behind, Carry-Forward Routed) matched what round-3
   surfaced naturally.

FRICTION (and proposed framework changes)

1. Citation form assumed spike-sourced deltas.
   The SKILL's canonical form is `[revised per <source-filename> §<delta-id>]`. This works for
   round-1/2 (where the source is `spike-3-landlock-probe.md §Δ-22` and grep is straightforward)
   but doesn't fit round-3, where deltas are sourced from `DECISIONS.md` D-entries and per-
   session closeouts. The literal SKILL form `[revised per DECISIONS.md §D501]` conflates the
   document type with the delta ID. Round-3 introduced two refined forms:
     - `[revised per DECISIONS.md D5XX (Δ-N), round-3]` for D-entry-sourced deltas
     - `[revised per closeouts/<file> §<id>, round-3]` for closeout-sourced deltas
   These are now in the spec's front-matter Evidence Convention list. SKILL-feedback: the SKILL
   should canonicalize a small family of citation forms that explicitly cover non-spike sources.

2. Audit file path was implicit.
   The SKILL's templates/deltas-applied.md comment says "Place at: findings/reimplementation-
   spec/DELTAS-APPLIED.md (Sibling of the spec)." Round-3 wasn't spike-driven, didn't fit under
   `findings/spikes/round-3/`, and the sibling-of-spec placement doesn't disambiguate between
   rounds. Round-3 used `findings/deltas-applied/round-3.md` (new directory) for round-numbered
   audit. SKILL-feedback: explicitly cover the non-spike case, possibly with a directory
   convention `findings/deltas-applied/round-N.md` for round-numbered passes; the spike-sibling
   form remains a special case.

3. Closeout filename collision-prone.
   The SKILL canonicalizes `closeouts/<YYYY-MM-DD>-spec-deltas.md` (single-shot per day).
   Round-3 used `closeouts/2026-05-03-spec-delta-3.md` to match the round-numbered vocabulary
   already present in the spec. Two passes on the same day would collide on the SKILL form.
   SKILL-feedback: round-numbered (or otherwise disambiguated) filename is worth adopting in
   the SKILL canonical.

4. BACKLOG.md existence assumed but not bootstrapped.
   The SKILL says "DEFER → Add to BACKLOG.md with rationale and a back-reference." The codex
   workspace did not have a `.codecarto/BACKLOG.md` before round-3. The upstream framework
   `.codecarto/BACKLOG.md` is for *framework feedback* deferrals — it is not a project-level
   BACKLOG. The codex workspace's selective sync correctly excluded the upstream BACKLOG (it
   would have been wrong to inherit framework deferrals into the project) but did not provide
   a project-level template to start from. Round-3 created `.codecarto/BACKLOG.md` from
   scratch with a project-scoped shape and a clarifying note. SKILL-feedback: ship a
   `templates/backlog-project.md` skeleton and reference it explicitly from the SKILL's DEFER
   step. Possibly also clarify the project-level vs framework-level distinction in
   GUIDE.md.

5. §header naming ("Post-Spike Revisions") didn't generalize.
   The spec's existing `## Post-Spike Revisions` header was shaped for spike-sourced rounds.
   Round-3 is post-pipeline pre-implementation but not spike-driven; the §header still reads
   "Post-Spike Revisions" for continuity. The Round-3 Revisions subsection makes this explicit
   in its first paragraph. A future framework cleanup pass could rename to "Post-Pipeline
   Revisions" or "Pre-Implementation Revisions" so the §header generalizes.

6. The SKILL doesn't address D-entry promotion semantics for DEFER.
   When Δ-38 was triaged DEFER, the source closeout had no D-entry; round-3 chose NOT to
   promote it to a D5xx entry (DEFERed items don't reflect a project decision; they reflect a
   project deferral). Instead, BACKLOG.md B1 captures the deferral. The SKILL says "Append
   numbered entries to DECISIONS.md for any decisions made during triage that weren't already
   in the deltas (e.g., 'rejected Δ7 because the spec already covered the case at §X')." This
   left ambiguous whether DEFER-with-rationale belongs in DECISIONS.md or BACKLOG.md. Round-3's
   reading: DECISIONS.md is for things the project decided to DO; BACKLOG.md is for things the
   project decided to DEFER. SKILL-feedback: clarify this distinction in the SKILL. The
   "Decisions Beyond Triage" section in DELTAS-APPLIED.md is for decisions made during the
   application that are independent of the deltas (e.g., refining D501's literal proposal),
   which IS what DECISIONS.md should capture; DEFER rationales go in BACKLOG.md.

7. SKILL Step 6 (citation conventions list) could be more prominent.
   Step 6 ("Update the spec's front-matter citation conventions list") is a one-liner in the
   SKILL but is load-bearing for Step 5's audit-table credibility — if the spec doesn't
   acknowledge the new citation forms, the audit-table marker list is unanchored. Round-3
   updated the front-matter list. SKILL-feedback: add a sentence to Step 6 emphasizing this
   is required when the application introduces new citation forms.

8. The mount-sync warning was warranted but not exercised.
   Round-3's edits were small and non-overlapping; no mount-sync issues observed. The
   boilerplate warning ("you may be working through a bash mount...") is good defense; round-3
   did not reach for the heavier mitigations (full-file overwrites, wc -l verification) but
   would have if needed.

DELTA-SPECIFIC NOTES

Δ-36 application refinement.
  D501's literal proposal was "map unknown done_reason to 'error'" — minimal. Round-3 refined
  to "emit error event + done(error)" mirroring the existing done_reason='error' row. The
  refinement is an example of "implementing session refines the prompt" but applied at a
  different layer: the implementing session (thaum-providers-ollama) raised the delta; the
  spec-delta-application session (this one) refined the proposal during application; the
  next implementing session (when thaum-providers-ollama implements the corrected spec) will
  validate the refinement is implementable. The SKILL didn't have explicit language for "the
  application refines the proposal", but the four-bucket matrix's APPLY bucket implicitly
  permits it. Worth elevating: the SKILL could note that APPLY may include refinements
  beyond the literal proposal text, with the refinement captured as a Decision-Beyond-Triage.

Δ-37 mechanical-but-not-trivial.
  Δ-37 looked mechanical (replace 8 occurrences of `'allowed-loopback'` with
  `'allowedLoopback'`) but required judgment on which sites to leave alone:
    - Round-3 subsection's Δ-37 row uses both forms (historical reference).
    - Per-`networkPolicy` table row's inline annotation: "(was hyphenated `'allowed-loopback'`)"
      preserves grep traceability for the old form.
  These two sites intentionally retain the old form. SKILL-feedback: mechanical wire-shape
  fixes still benefit from an audit-table that names every site; the round-3 audit's "Citation
  Markers Added" section serves this purpose and was load-bearing.

Δ-38 DEFER rationale.
  The reshape is well-scoped and the BACKLOG entry's "Smallest viable form" line is concrete,
  but the right model-facing-name choice (codex-names via shim vs v0-names native) needs the
  delivery surfaces (cli, tui) to be visible. DEFER was the honest call. The SKILL's DEFER
  bucket worked as documented. SKILL-feedback: the BACKLOG entry's preconditions list (which
  modules need to land before the deferral can be revisited) is not in the SKILL's templates
  but proved valuable; consider promoting to the BACKLOG-template skeleton.

OVERALL

This was a clean first run. The SKILL's posture, discipline, and outputs are all in the right
shape. The friction items above are refinements, not revisions — none of them indicate the
SKILL is wrongly-shaped. Round-4 (whenever the next spec-delta-application session runs) will
be cheaper than round-3 was; round-3 absorbed the first-time cost of working out the citation
forms, the audit-file path, the BACKLOG semantics, and the closeout-filename convention.

The orchestrator role (cross-session context, accumulated conventions in CONVENTIONS.md, D-entry
discipline in DECISIONS.md, project-level deferrals in BACKLOG.md) is doing exactly what the
2026-05-02 framework feedback pass intended. Round-3 inherited 12 conventions, 23 decisions
(D001-D223), and the Round 1+2 revision history; added 0 conventions, 2 decision dispositions
(D501-D502 marked APPLIED), and 1 BACKLOG entry (B1). The compounded shape is durable.
