✅ SDK v2.0.0 Published — Major Package Restructuring

The TypeScript SDK has been published as v2.0.0 (~July 27, 2026) with full support for the 2026-07-28 spec. However, it's a major restructure — the old monolithic @modelcontextprotocol/sdk package has been split into multiple scoped packages:

Old (v1.30.0)New (v2.0.0)Purpose
@modelcontextprotocol/sdk@modelcontextprotocol/serverServer-side code (tools, transports)
@modelcontextprotocol/sdk@modelcontextprotocol/clientClient-side code
(internal)@modelcontextprotocol/coreShared Zod schemas (spec + OAuth)
(internal)@modelcontextprotocol/server-legacyBackward-compat with v1 initialize era
—@modelcontextprotocol/codemodAutomated import rewriter for v1→v2 migration
—@modelcontextprotocol/node, hono, express, fastifyTransport adapters

Key facts from the release notes:

  • Beta release — "First beta release of SDK v2 with support for the MCP 2026-07-28 specification revision"
  • Codemod available — @modelcontextprotocol/codemod automates import rewrites from v1 paths to v2 package roots
  • Migration guides — docs/migration/upgrade-to-v2.md (v1→v2) and docs/migration/support-2026-07-28.md (spec adoption)
  • server/discover built in — DiscoverResult, _meta['io.modelcontextprotocol/serverInfo'] aligned with spec PR #3002
  • Legacy support — @modelcontextprotocol/server-legacy provides dual-era backward compatibility
  • Breaking type changes — DiscoverResult no longer has body serverInfo (moved to _meta); clientInfo is now optional (SHOULD, not MUST)

Impact on CodeCartographer: The package.json dependency "@modelcontextprotocol/sdk": "^1.29.0" must be replaced with "@modelcontextprotocol/server": "^2.0.0", and all imports in server.ts must be rewritten. The codemod automates most of this.

📋 Spec 2026-07-28 Change Analysis vs. Current Server

The 2026-07-28 revision introduces 9 major changes and 12 minor changes. Below is each major change mapped to its impact on the CodeCartographer MCP server.

1. Removal of Protocol-Level Sessions & Mcp-Session-Id Header

SEP-2575 · Breaking SDK v2 handles

Spec requiresNo session state. List endpoints (tools/list) no longer vary per-connection. Cross-call state uses explicit server-minted handles as ordinary tool arguments.
Current stateThe server is already effectively stateless — every tool takes an absolute cwd parameter and operates on filesystem state. The Server class from the SDK manages the initialize handshake and session internally, but CodeCartographer's handlers don't rely on it.
ImpactLow for application logic, handled by SDK v2. The new @modelcontextprotocol/server v2.0.0 removes the initialize handshake and implements the stateless protocol. For dual-era support, @modelcontextprotocol/server-legacy preserves backward compat.
EffortMinimal code change if SDK upgrades cleanly; otherwise requires removing the SDK's Server class and implementing raw JSON-RPC message handling.

2. Stateless Protocol: Remove initialize Handshake, Add Per-Request _meta

SEP-2575 · Breaking SDK v2 handles

Spec requires Every request MUST include in _meta:
  • io.modelcontextprotocol/protocolVersion (required) — e.g. "2026-07-28"
  • io.modelcontextprotocol/clientCapabilities (required)
  • io.modelcontextprotocol/clientInfo (optional, SHOULD include — demoted from required per spec PR #3002)
Servers SHOULD include io.modelcontextprotocol/serverInfo in each result's _meta.
Current stateThe SDK's Server class handles initialize internally, exchanging protocol version and capabilities in a handshake. No per-request _meta is processed. The buildServer() function constructs new Server({name, version}, {capabilities: {tools: {}}}) — the SDK does the rest.
ImpactHandled by SDK v2. The new @modelcontextprotocol/server v2.0.0 implements per-request _meta processing, stamps serverInfo on every response, and aligns with spec PR #3002 (serverInfo in result _meta, not body). The server code only needs the import rewrite + package.json update.
Code locationserver.ts:1103-1128 — buildServer() and startStdioServer()

3. New server/discover RPC (MUST Implement)

SEP-2575 · Required SDK v2 built-in

Spec requires Servers MUST implement server/discover RPC. Returns:
  • supportedVersions — array of protocol versions
  • capabilities — what the server supports (tools, resources, prompts)
  • _meta['io.modelcontextprotocol/serverInfo'] — name + version
  • instructions — optional LLM guidance
  • ttlMs + cacheScope — caching hints
Current stateNo server/discover handler exists. The server relies entirely on the SDK's initialize handshake.
ImpactMust add a new handler that returns server metadata. This is a new ~30-line handler plus registration in the SDK's request handler map.
Implementation sketch 
// New handler to add
function handleDiscover() {
  return {
    resultType: "complete",
    supportedVersions: ["2026-07-28"],
    capabilities: { tools: {} },
    _meta: {
      "io.modelcontextprotocol/serverInfo": {
        name: "codecartographer",
        version: PACKAGE_VERSION,
      },
    },
    instructions: "CodeCartographer reverse-engineering framework.",
    ttlMs: 3600000,
    cacheScope: "public",
  };
}

6. Tasks Extension (io.modelcontextprotocol/tasks)

SEP-1686/2663 · Optional New extension

Spec requiresTasks extension is now official. Provides async long-running ops with polling (tasks/get), mid-flight input (tasks/update), durable handles. Servers MAY implement it.
Current stateNo tasks extension. All operations are synchronous request/response — the server returns prompt text and the host drives execution.
ImpactOptional future enhancement. Could be useful for long-running pipeline phases that need polling, but not required for spec compliance.

7. Multi Round-Trip Requests (MRTR) Pattern

SEP-2322 · Optional for this server New pattern

Spec requires Servers MAY respond to tools/call with InputRequiredResult (resultType: "input_required") to request additional input (elicitation, sampling, roots). Client retries with inputResponses + requestState.
Current stateAll 18 tools return plain text results via textResult() helper. No input-required flows. The server is purely synchronous: call → get prompt text → host executes.
ImpactNot required — servers MAY use MRTR but don't have to. If added later, the textResult() helper and handler return types would need to support the InputRequiredResult shape.
Code locationserver.ts:105-111 — textResult() helper would need a sibling for MRTR results

8. resultType Field on All Results

SEP-2322 · Required SDK v2 handles

Spec requires Every result MUST include resultType: "complete" (for normal results) or resultType: "input_required" (for MRTR). Clients MUST treat absent resultType as "complete" for backward compatibility.
Current state The textResult() helper returns: 
{ content: [{ type: "text", text }] }
No resultType field. The SDK's CallToolRequestSchema response type doesn't include it.
Impact Handled by SDK v2. The new SDK's 2026-era wire schemas require resultType on results. If the SDK doesn't add it automatically on tool call results, the textResult() helper is the single point of change: 
function textResult(text, structured) {
  return {
    resultType: "complete",
    content: [{ type: "text", text }],
    ...(structured ? { structuredContent: structured } : {}),
  };
}
Code locationserver.ts:105-111

Current stateServer is stdio-only. No HTTP transport, no SSE.
ImpactNone.

⚠️ Risk: Dropping Legacy Host Support

If the server upgrades to modern-only (no dual-era), it will break compatibility with hosts that still use the initialize handshake. Given that CodeCartographer's README lists Claude Code, Codex, opencode, Cursor as target hosts, the upgrade should verify that each host has migrated to the 2026-07-28 protocol — or implement dual-era support.

Recommendation: Implement dual-era support initially. Once all target hosts confirm modern protocol support, legacy can be dropped.
