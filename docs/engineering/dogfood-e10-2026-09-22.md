## Inspection

- **My first row for the Pi extension was wrong, in the direction the template is designed to catch.** I wrote one row — "partial, no test drives the slash commands" — from memory. Checking the source turned up 48 headless tests across handlers, activation, the `tool_call` policy and the auto-runner. The honest shape is *two* rows: the decision logic is `observed fact` and fully addressable; only the rendered widget and live sub-agent lifecycle lack a headless route. A single coarse row would have recorded a hazard against the whole surface that exists for a fifth of it. Granularity is the difference between a useful hazard and a false one, and the template's "one row per surface or concern" is what forced the split.
- **The narrowed hazard is still real.** Nothing asserts what a Pi user sees. E10 does not fix that and must not: the SKILL says record the gap, do not propose a rewrite. It is now written down where a planning phase will read it, at the right granularity.
- **"Environment unavailable" is a distinct state from "no route."** The #435 row has a perfectly good headless test; what is missing is a Windows machine. The template's `Evidence: open question` plus the note carries that; the spec-side `Verification route` would still say `test`, and the slice would still be blocked. The vocabulary distinguishes the two, which is what step 3 of the issue asked for.
- **Cost is a constraint, not a gap.** Broad-Side's only end-to-end route spends money. It is documented and runnable, so it is a `run` route with an integration constraint, not `none`. The distinction matters because a route that exists but is expensive should not read as "unobservable."

## What the lifter does with the routes

The spec-side `Verification route` column lifts into `verification_route` in E01's `check_kind` vocabulary. `none` lifts as a refusal (`no-route`) while still recording `"none"` on the slice, so a plan cannot be derived from an artifact that admits a slice is unobservable — but the admission survives in the data for a reviewer. A blank cell is refused (write `none` if you mean none), and a route outside the vocabulary is refused with the vocabulary named. Tested in `tests/engineering-lift.test.mjs`.

**Where the route stops, stated plainly.** It stops at the lifter. E04's `SliceInput` has no `verification_route` field and `buildChangePlan` ignores unknown fields; the plan's `check_kind` lives on `proof_obligations`, which the lifter does not build (a scenario is a claim; a proof obligation is a specific check against it, and writing one from a table row would be inventing evidence). So today the route is refused-or-recorded at the artifact and does not reach the plan. Carrying it forward — a lifted route becoming the `check_kind` of a proof obligation the host must discharge — is E11's loop, where a host actually runs something. E10's contract is the narrower one the issue states: outputs *identify* usable proof boundaries and honestly report unavailable ones.

## Limits

- Filled by hand, not by a model session running the architecture phase. The instruction exists and the invariants prove it; whether a session fills the table well is the unfinished half of step 5, the same gap E09's dogfood recorded.
- One fixture, and it is our own repository. A GUI-first or hardware-bound codebase would exercise the `manual-procedure` and `none` paths much harder than this one does; here every row but one has a headless route.
- The porting-phase table (`reverse-engineering-bundle.md`) was not filled; its instruction is to carry forward and sharpen this one.
