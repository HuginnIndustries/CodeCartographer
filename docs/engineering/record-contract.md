# Engineering records: v1 design contract

**Status:** design baseline for E01, not a shipped schema. E01 must add executable schema fixtures and close the approval-interface question before dependent tasks implement it. No later issue may independently redefine this contract. Read [vision](vision.md) and [implementation plan](implementation-plan.md).

## Ownership and proposed layout

New runtime code lives under `core/engineering/`, with a one-way barrel exported by `core/index.ts`. Existing `core/status.ts`, analysis completion, and `workflow/status.yaml` are not repurposed. Avoid widening the existing large MCP handler file: new registration/handlers should delegate to a focused engineering adapter module.

Proposed additive workspace namespace (freeze in E01):

```text
.codecarto/engineering/
  changes/<change-id>/
    change.json
    brief.md
    plan.md
    slices/<slice-id>/slice.json
    attempts/<attempt-id>/
      attempt.json
      snapshots/<snapshot-id>.json
      proofs/<proof-id>.json
      reviews/<review-id>.json
      approvals/<approval-id>.json
      artifacts/<artifact-id>
```

`change.json` and `slice.json` are versioned mutable projections, updated through the framework with compare-and-swap revision checks. Attempt observations are create-only, immutable once finalized; a corrected observation is a new record referencing the superseded one. No global mutable project registry is required initially: enumerate valid change directories and report corrupt ones explicitly. Do not let one malformed record erase visibility of other changes.

Use opaque, path-safe IDs generated by the core. Slugs/titles are display metadata, never arbitrary filesystem paths. E01 fixes the exact ID grammar and record envelopes. Reject traversal, separator tricks, duplicates, symlink escapes, and unknown incompatible schema versions. Never trust a host-supplied absolute artifact path as an output destination.

## Minimum entities

| Entity | Required meaning |
|---|---|
| Change | Schema version, ID, title, mode, requested outcome, baseline reference, scope/non-goals, preserved contracts, acceptance scenarios, optional references, revision |
| Slice | ID, change ID, deliverable, scenario IDs proved, dependency IDs, proof obligations, permitted scope, revision |
| Attempt | ID, change/slice IDs, plan/input identity, baseline/candidate snapshot IDs, start/end, outcome, parent/superseded attempt if any |
| Snapshot | Repository baseline identity, sorted repository-relative content manifest, dirty/relevant untracked identity, input/plan hashes, coverage/exclusions, stable digest |
| Proof | ID, attempt/scenario/snapshot binding, check kind, observed result, start/end, exit code when applicable, sanitized artifact references and digests, collector/provenance |
| Review | ID, attempt/snapshot/input bindings, reviewer/author context separation declaration, objections and evidence, dispositions, remaining blockers |
| Approval | ID, exact accepted change/slice/attempt and input/candidate digests, human decision, host-controlled receipt reference, authority provenance, time |

A claim record is not a proof record merely because it contains `result: passed`. The collector identifies the observation boundary: `host-observed`, `ci-reported`, `manual-observation`, or `agent-claimed`. E01 fixes exact enum spelling in schemas. `agent-claimed` does not satisfy a required observed check. GUI/manual proof is possible but must identify its procedure and source; it is not silently treated as a successful shell test.

## Identity and freshness

1. Record the Git base when present, but do not identify an implementation with HEAD alone. Dirty tracked bytes, relevant new files, deleted files, and file types matter.
2. The host captures implementation manifests; the framework validates and compares records. Existing framework read-only Git/file utilities may be reused, but no framework path starts arbitrary proof commands.
3. The initial safety rule is conservative: changes in a declared input, plan, scoped candidate, or relevant environment descriptor invalidate the affected acceptance. Unknown coverage means revalidation or blocked—not assumed freshness.
4. Use portable repository-relative paths in published artifacts; normalize a documented encoding and deterministic sort. Distinguish executable mode and symlink entries where relevant. Do not dereference an escaping symlink or ingest secrets to make a fingerprint look complete.
5. Exclude the engineering namespace and generated evidence from the implementation fingerprint to avoid self-invalidation. Include the actual brief, plan, and selected-reference bytes in a separate input digest. Document ignored/generated exclusions and flag relevant uncovered inputs.
6. Capture must detect a moving source during collection or record it as unstable. Pre-acceptance recheck prevents a candidate edited after proof from inheriting that proof. E01 specifies host collection/freeze semantics; a host that cannot attest a stable candidate cannot finalize acceptance.
7. A fingerprint establishes identity, not correctness. It is not a substitute for the proof's environment, provenance, or actual outcome.
8. New attempt IDs preserve prior failed or superseded results. Resume locates existing attempts; it does not silently rerun an external command or repeat a side effect.

## State and outcome semantics

Initial change states: `draft`, `planned`, `active`, `blocked`, `accepted`, `abandoned`. Staleness is a validity condition computed against records and shown explicitly; old acceptance remains historical but is not current approval for different bytes.

Attempt outcomes distinguish `running`, `failed`, `blocked`, `ready-for-review`, `needs-human-acceptance`, `accepted`, and `superseded`. E01 may refine representation while preserving these distinctions; dependent issues consume the merged schema.

- Missing environment, permission, input, or acceptance is **blocked**, not a failed test.
- A completed test returning a failing result is **failed**.
- No record may transition to accepted with missing required observed proof, stale bindings, an unresolved blocking objection, or missing authorized human acceptance.
- A slice starts only after its declared dependencies are currently accepted for the identities the plan expects. Do not confuse file creation order with DAG eligibility.
- The first pilot is serial. File locking/CAS protects retries and accidental concurrent writers; it is not a distributed scheduler.
- Starting a second change creates a separate identity and never backs up/replaces the first change's directory.

## Gates: structure is not semantics

The gate's deterministic half checks record schemas, reference existence, identity bindings, scenario coverage, dependencies, completed outcomes, objection dispositions, and authority provenance. It does not claim to independently prove semantic correctness of code or tests.

Independent review examines whether tests meaningfully exercise the requested and preserved behavior, traces concrete failure modes, and challenges unsupported claims. Record context separation; do not describe a reviewer ID string as cryptographic proof of independence.

A blocking objection remains blocking until evidence resolves it. The initial pilot has no automatic waiver. Later accepted-risk policies must explicitly bind authority, scope, and candidate identity; “has owner” or “box checked” cannot implement that policy alone.

The existing analysis `validatePhaseOutput` remains backward compatible. New engineering gates use explicit records rather than parsing a model-written PASS table as execution evidence. Any future tightening of legacy validation must be separately version-gated and tested on old workspaces.

## Human approval and threat boundary — E01 release gate

A general agent-callable `approve: true` is not a human approval channel. The host owns interaction with the user and authorization; the framework consumes its bounded receipt. E01 must specify:

- how the host shows the exact scope, candidate identity, proof/review summary, and remaining limitations;
- how the resulting receipt reaches the core through a trusted path not mintable by the ordinary agent tool interface;
- how stale, replayed, cross-change, or mismatched receipts are rejected;
- what is attested versus actually authenticated in a given adapter;
- how a host without this capability returns `needs-human-acceptance` without bypassing the gate.

Manual Markdown edits or same-user filesystem records alone cannot authenticate who approved. They may be useful cooperative records, but must be labeled as such and cannot be advertised as tamper-proof authorization. Hashes alone cannot authenticate a person. Do not introduce a homemade credential system, store tokens in `.codecarto/`, or claim universal secure acceptance across all MCP clients.

**Implementation readiness:** all tasks depending on E01 wait for E01 to be fully merged and closed, including its reviewed host-approval contract. There is no implicit schema-only sub-gate. E09/E10 are the independent template workstream. If no minimal trustworthy approval path is available, the pilot may stop at a reviewable candidate, but E01 and the end-to-end acceptance criterion remain incomplete. Record the gap rather than weakening “accepted.”

## Host protocol and proposed public API

Use one additive, experimental MCP surface, proposed name `codecarto_change`, backed by typed core operations. Initial action vocabulary: `create`, `status`, `plan`, `start-attempt`, `record-proof`, `record-review`, `check`, `request-acceptance`. The trusted host-approval integration is separate from generic agent-authored payloads; `request-acceptance` does not grant acceptance.

E01 freezes exact arguments, result/error schemas, capability negotiation, and idempotency/CAS behavior before E07 registers tools. Responses must carry usable text and structured content, with the same semantic result. Empty libraries are valid for `create`/`plan`. Existing analysis/synthesis tools and their phase gates remain unchanged. Do not bypass their guard by overloading `codecarto_phase` with an engineering phase.

The host receives the next bounded action and permitted scope, executes it using its own tool/permission system, and returns observed records. Retries of record ingestion are idempotent; retries of external commands are never inferred from a lost acknowledgement. Bounded time, cost, and retry policies belong to the host and change constraints. The framework can report exhaustion; it does not silently spend or retry forever.

Drop-in templates may describe the procedure but cannot claim runtime enforcement. Pi initially can display records/read status without allowing source edits or shell execution in analysis mode. Rich Pi build integration is a separate future design.

## Storage, security, and public export

**Distribution isolation is part of E02, not later release polish.** This repository's `.codecarto/` can be both live workspace and distributable template. Exclude the entire engineering runtime namespace from template copying and npm package files, and add default ignore rules in both the workspace `.gitignore` and shipped `templates/gitignore`. Keep shareable documentation/templates outside it. Test with synthetic histories, approval records, and artifacts that neither a newly initialized workspace nor a packed tarball receives another project's state. Deliberate sanitized export is a separate action; tracking a record intentionally never makes it template content.

Reuse the project's atomic write/containment/locking primitives where their contracts fit. Test rejection of malformed, truncated, cross-linked, and unsupported records; crash before and after the commit point; duplicate requests; stale revisions; and concurrent attempts. An accepted projection cannot precede durable records it references.

Raw stdout, environment variables, commands with embedded credentials, arbitrary file contents, and private repository identity are not automatically exportable. Keep evidence local by default. Store sanitized summaries and references; when a log is deliberately retained, distinguish the digest of raw local bytes from the digest of the sanitized export. Export is an explicit reviewed operation, not a side effect of acceptance or library publication.

No new database, network service, telemetry backend, provider dependency, release automation, or credential vault is needed for the first pilot.
