# Lifecycle vision dogfood — 2026-09-17

**Scope:** a hands-on test of existing planning, state, reuse, and validation boundaries, followed by an independent design critique. **Not** a complete Traverse run, a delivered engineering feature, a productivity benchmark, or a live Pi integration test.

**Source baseline:** CodeCartographer v0.26.0, commit [`ca071ff1e2df63a830bbbb49dc3baa5d8c9ed162`](https://github.com/HuginnIndustries/CodeCartographer/commit/ca071ff1e2df63a830bbbb49dc3baa5d8c9ed162). The documentation branch subsequently starts from the newer documentation-only main commit; the experiment's baseline does not move with it.

## Method and publication boundary

A disposable source snapshot, separate analysis workspaces, and a private disposable library were used. The experiment invoked actual exported public MCP handler functions and core code, isolating user configuration with `CODECARTO_USER_CONFIG_PATH`. This exercises handler/core behavior, not MCP stdio transport or a remote server. Existing installed dependencies were used read-only. No provider calls or source changes were needed.

The real trial captured the requested lifecycle vision, wrote proper artifacts and handoffs, validated/completed vision capture and reference proposal, and stopped at the unchecked-selection gate. It did not claim completion of merge, finalization, or implementation. Intentionally invalid artifacts were kept in separate, explicitly labeled negative-control workspaces.

This is a sanitized report. Raw transcripts, absolute workstation paths, user identifiers, environment details, and local execution archives are deliberately not checked in. No claim depends on a private path a reader cannot access; source anchors and repeatable test steps are given below. The raw local observations informed this summary but are not presented as independently reproduced public CI evidence.

## Source evidence and interpretation

Read these files at the pinned commit when reproducing:

- `core/synthesis.ts`, `runPhasePreflight`: nonempty library and checked reference/version requirements.
- `core/prompts.ts`, `buildPhasePrompt`: forward-synthesis framing excludes treating the surrounding repository as source to reverse-engineer.
- `core/pipeline.ts`, `validatePhaseOutput`: parses the artifact's rows and Overall line, plus findings checks; it does not execute tests or compare those rows to every declared completion criterion.
- `mcp-server/server.ts`, `handleInit`, `handleStatus`, `handleValidate`, `handleComplete`, `handleNext`: public handler boundaries exercised.
- `.codecarto/workflow/pipeline-synthesis.yaml`: four-phase dependency/criteria definition and fixed output paths.
- `self-audit/2026-09-15-v0.25.0-full-with-deep-audit/findings/reimplementation-spec/reimplementation-spec.md`, System Summary: explicitly a new implementation, not a patch queue; defects become proposed design consequences.

The historical spec's scope matters. Importing it as the baseline for an in-place feature could confuse recommended architecture with implemented behavior. The trial marked it historical and unverified. Its importer defaulted analysis time to the import time because original timestamp metadata was not supplied; that default is **not** a fresh analysis. A real migration should preserve original generation/analysis provenance separately from publication/import time.

## Portable reproduction recipe

Use a fresh disposable checkout of the pinned revision and inspect its scripts before installing dependencies. Keep the active trial outside the source's template `.codecarto/` directory. Configure a separate `CODECARTO_USER_CONFIG_PATH`; do not call a library-init operation that changes a real global library location. Use documented marker/workspace-local config for the temporary library.

1. Import `handleInit`, `handleNext`, `handleValidate`, `handleComplete`, and `handleStatus` from the snapshot's `mcp-server/server.ts` with a TypeScript-capable Node invocation.
2. Initialize `synthesis`; write a genuine input vision and the matching captured output/handoff. Validate, complete, and read status back.
3. Request next first without a library, then with an empty marked library. Record the actual refusal rather than creating a fake dependency.
4. For DF-06 only, create a separate TEST ONLY workspace and a negative artifact containing no substantive required sections, a standard Validation table with one invented criterion marked PASS, and an Overall PASS. Supply a handoff identifying it as test data. Observe validation/completion without reporting it as real analysis.
5. Copy the genuine trial for DF-07; replace its raw vision with a different goal and read status. Preserve both input identities so the change is demonstrable.
6. For reuse, stage the historical spec inside the temporary workspace before publication, read the entry back, and leave all candidate selections unchecked. Observe the refusal at merge.
7. Reinitialize an occupied trial without `force` and capture the refusal. Do not use destructive reset to manufacture continuity.
8. Preserve observations with the exact revision and test commands. Check the original checkout's HEAD/status; do not publish raw machine logs without a separate information review.

## What changed in the recommended vision

- Make an in-place engineering change first-class; optional references are not compulsory synthesis inputs.
- Separate project knowledge, change, slice, and attempt; preserve repeated and failed work.
- Move minimal evidence identity, conservative freshness, and honest acceptance ahead of autonomous advancement.
- Distinguish observed current behavior from proposed redesign and verified implementation in reusable knowledge.
- Prove one thin end-to-end maintenance loop before building a large release/team subsystem.
- Scale investigation and process overhead to the task; prefer fast verification seams without universally demanding a new CLI.

An independent read-only critique agreed with these priorities and highlighted host authority and appropriate non-headless proof. That reviewer did not see the later freshness/negative-control captures before finishing; DF-06–DF-09 are primary-run observations, not attributed to an independent reproduction.

## Limits retained from the run

No full Traverse execution, actual code change, end-user acceptance, release, deployment, multi-host comparison, or performance/cost comparison occurred. A proposal completion produced a non-gating authoring warning: a closed question ID appeared in the handoff but not verbatim in the proposal body. That is an authoring limitation, not evidence of a framework defect. The new implementation plan requires question/objection closures to remain visible and linked in both records and human reports.

See the [implementation plan](implementation-plan.md) for the gated work derived from these findings. This report is not permission to implement or release all of that work at once.
