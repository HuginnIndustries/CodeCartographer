# v0.12.x discoverability and launch plan

Date: 2026-07-21
Last reconciled: 2026-07-23
Status: active — release and Registry gates complete; proof package next
Owner: maintainer, unless reassigned below

## Objective

Ship a small, truthful discoverability release that makes CodeCartographer
discoverable as both an evidence-backed reverse-engineering tool and a
human-gated software-planning tool. v0.12.1 delivered the storefront and package
metadata; v0.12.2 corrected the case-sensitive GitHub organization namespace and
became the first version published to the official MCP Registry. v0.12.3 fixed
single-shot `/codecarto-next` phase completion and is the current release across
npm, GitHub, the website, and the Registry. Support that positioning with
inspectable case studies, and only then use short-lived launch channels to
amplify the durable assets.

The launch is successful when a new user can discover CodeCartographer, install
the published package, understand both directions of the workflow, inspect real
evidence and provenance, and reproduce the relevant demo without relying on a
launch post.

## Launch principles

1. **Truth before reach.** Do not announce broadly while npm, GitHub, the MCP
   Registry, and the website disagree about the product.
2. **Proof before positioning.** Lead with inspectable artifacts and one clear
   workflow, not a long feature list.
3. **Gates before dates.** The seven-day schedule is a target. A failed gate
   moves the launch; it does not get waived to preserve a date.
4. **One canonical story.** All surfaces should use the same two-direction
   description: repositories become evidence-backed specifications; confirmed
   specifications plus a vision become provenance-backed plans.
5. **Durable assets first.** Registry metadata, examples, documentation, and
   video should continue producing discovery after launch-day traffic ends.
6. **Manual first, automate second.** Perform the first MCP Registry publication
   manually, record the exact working process, then automate it after the release
   is verifiably indexed.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| MCP namespace is rejected after npm publish | Keep the exact-case `io.github.HuginnIndustries/*` owner grant locked by release invariants and validate it before future tags |
| Registry preview changes schema or resets data | Generate with the current publisher, pin its version in automation, and add a scheduled API check |
| Website and repository drift again | Add a cross-repository release consistency check; deploy the site only from a published version |
| Case studies become unreviewable artifact dumps | Provide short indexes, three highlighted claims, direct artifact links, and explicit limitations |
| A live LLM run produces weak or irreproducible output | Pin inputs/model/options, retain raw artifacts, distinguish runtime correctness from semantic quality, and do not cherry-pick silently |
| Launch copy overclaims broad compatibility | Test named paths, distinguish Pi/MCP/drop-in behavior, and keep experimental limitations visible |
| Several launches exhaust response capacity | Give Show HN a dedicated day; stagger other channels and pause if substantive feedback arrives |
| Promotion violates community norms | Follow each channel's current rules, never solicit votes, and keep HN conversation personally authored |
| Product Hunt assets force premature launch | Prepare and schedule on Day 7; launch only when all three cases and account requirements are ready |
